# Game client notes

Moved from [development.md](../development.md) on 2026-11-07.

## Game client (M5b)

A person plays a skirmish against our AI from the main menu to the end screen, natively (`cargo run -p glasnost-platform-native -- --game --game-dir DIR`) and on the web (`?mode=game`, docs/web.md). The interface is our own code, `glasnost-ui` (no egui), drawn by `glasnost_render::batch2d` within the WebGL2 core.

- **Screens (`glasnost_ui::shell`).** Main menu, then skirmish setup (S-0412), then the game, then the end screen (S-0414), then back to the menu. The setup offers every multiplayer map with at least two start positions (S-0009 claim 23, `install::start_count`). Maps are known by their position in the list and, in the game, by a content hash (`session::content_hash`), never by a stock name. Lobby colours are the colour slots of S-0103 claim 10.
- **Modules (`crates/app/src/game`).**
  - `install` reads what the menus need from the mounted install: the base rules (setup values, S-0412 Import mapping), the maps and their start counts, the sound names, the sound and speech databases and the sample bank.
  - `play` is the running game without drawing: selection, tools (select, place, sell, repair, power), sidebar clicks (`econ::sidebar::click`), status messages and the end screen. Every order goes through `glasnost_ai::game::Game::issue`, so it is in the replay.
  - `session` is a game on a loaded map: camera (S-0101 limits), the live scene, radar, gestures, and the HUD's draw list.
  - `paint` turns draw lists into batch quads, and draws them on the CPU for tests.
  - `client` holds the screens, jobs, pacing, sound and input, without a window.
  - `window` runs winit and wgpu. The battlefield is drawn on the GPU (`map_gpu::MapRenderer` into a target the batch shows through `Batch2d::set_image_view`); if that fails, it falls back to the CPU compose.
- **Pacing.** `mapview::live::Pacer` gives one tick per drawn frame at most, measured from each cycle's start (S-0201 claims 2 to 4). A tick that falls due between two drawn frames runs in the later one, but its cycle starts when it fell due, as long as the frame before came earlier and at most one period ago. So a 75 or 144 Hz display keeps 62.5 ticks a second at 16 ms, and a late frame or a stall still restarts the cycle at its own time, with no catch-up (design: render (#76)). The network path tells the pacer of the frames on which it ran no tick (`Pacer::waited`). In a skirmish nothing ticks while the options menu is open (claim 8) or the window is out of focus (claim 9). The speed comes from the setup and the options menu. A network game paces by its own table (`setup::net_period_ms`, S-0201 claim 17 and F5), and neither the menu nor lost focus stops it (claims 15 and 16).
- **Sound.** `Audio` is created at the first game start and resumed on the first gesture. At each game start the client sets it up from the install's sound and speech databases, bank and names, under the game's quirk switches (S-0701). After each tick it calls `tick`. After input it calls `selected`, `ordered`, `key` and `cue`, with what `play` collected in `selected`, `acks`, `keys` and `cues`. Each frame it calls `set_view` and `frame`. Game-side choices use the unsynchronised stream seeded with the game's seed (S-0202 claim 8).
- **Input.** Clicks go through `glasnost_sim::targeting` (S-0214). A left release selects or orders (claim 26), a left drag is the band box, a right release clears the selection or ends a sidebar or placement mode (claims 26 and 28), and a right drag past F8 (8 pixels on either axis, `band::RightDrag`) scrolls the view (S-0101 claims 16 and 17) and is released with no effect (claim 27). The key commands are S-0213 table T2. Box selection, scrolling and key bindings follow those claims; the client's remaining interim rules are in the table below.

### Touch and touchpad scrolling (our own design)

The lead asked for this on 2026-11-10. It is not in any spec, so the code marks each rule `// design: touch and touchpad scrolling (lead's request 2026-11-10)`. It is client input only: no simulation state, save, replay or network order changes. Touch input is always on: before it, touches did nothing, so there is nothing to keep by turning it off. The settings screen's last row, *Touchpad scrolling*, turns off the touchpad path only (`Settings::touchpad_scroll`, on by default, stored as `touchpad=0` only when off; the key's first name, `touch=0`, is read the same way). Off, every wheel event is as it was before.

- **Touchpad swipe.** A wheel event with a pixel delta (winit's `PixelDelta`; in the browser `deltaMode` 0) over the battlefield view pans the view on both axes, the content following the fingers (`Client::wheel_event`, `Client::pixel_wheel`, `Session::pan`). Over the sidebar the pixels gather into rows of the icon strip, one row per row height (`hud::Layout::row_pitch`, 56 px at 100 % interface size), each row one S-0411 claim 18 wheel step; turning back starts the count again. A line delta stays one row per event wherever the pointer is.
- **Wheel notches in a browser.** Chromium reports a notched mouse wheel in pixels too, so in the browser a pixel delta with no horizontal part whose vertical part is a whole, non-zero number of 100 or 120 CSS pixels (the physical delta divided by the device pixel ratio) is read as a line delta: one strip row, no pan (`touch::WheelDelta::from_pixels`). Natively (winit on Wayland and macOS) a pixel delta is always a touchpad's. A touchpad swipe that moves exactly 100 or 120 CSS pixels straight up or down in one event is read as a notch now and then: one strip row instead of a pan.
- **Touch.** `game::touch::Touches` recognises the gestures, whatever the setting. One finger dragged past a slop of 10 view pixels on the battlefield pans the view so the content stays under the finger; on the sidebar a vertical drag steps the strip by rows. A finger lifted within the slop is a tap: a left press and release there. Two fingers both down and up within the slop and within 300 ms of the first one touching are a right press and release at their midpoint. A third finger, or a finger added to a drag, spoils the tap. Taps work on every screen; drags only in a running game. There is no fling.
- **Limits.** Every pan goes through `Session::scroll`, so F5 limits it (S-0101 claim 8). It is refused, as edge scrolling is, during an order block (S-0201 claim 14), while the window is unfocused and while the options menu is open. A touch never leaves the pointer behind: a tap's click ends with the pointer gone, and a drag does not move it, so no edge scroll starts from a finger.
- **Mouse events made of touches.** While a finger is down and for 500 ms after the last touch event, the window drops mouse moves and buttons, so a system that also turns touches into mouse events does not click twice. Only seen touches start it; a mouse-only machine never drops anything.
- **Browser page.** The canvas has `touch-action: none`, no text selection, no callout and no tap highlight; the page has `overscroll-behavior: none` and cancels Safari's `gesture*` events (pinch zoom).
- **Probe.** `?probe=1` on the web page puts the game's view centre and selection count into `data-glasnost-view` and `data-glasnost-selected` on `<body>`, for the browser check (`web-tests/touch.mjs`).

Known limits (touch): winit gives touchpads on X11 and Windows as line deltas, so those swipes stay one strip row per event and do not pan; a browser mouse whose notch is not 100 or 120 CSS pixels (a smooth-scrolling or accelerated wheel, as Safari's on macOS can be) still pans the view with the setting on; the iPad Safari settings and the Windows touch-to-mouse handling are untested on a device.

### Display scale and readable text (our own design)

The lead asked on 2026-11-10 for more readable interface text and for the game to have the right size on 2x displays. No spec covers either, so the code marks each rule `// design: readable text and display scale (lead's request 2026-11-10)`. It is client presentation and input only: no simulation state, save, replay, wire or golden changes.

**View pixels.** The client draws the whole picture (battlefield, sidebar, every screen) in *view pixels* and the window shows each view pixel as a square of `factor × factor` screen pixels, nearest-neighbour, so art stays crisp (`game::display`). Before, a window on a 2x display drew one art pixel per screen pixel: everything was half its size and the battlefield showed four times the area. Every spec'd pixel metric (the battlefield, the sidebar's layout, the radar, the status lines of S-0213 claim 25 in GAME.FNT, the tips) stays in view pixels and so keeps its meaning.

- **Factor.** The *Display scale* setting (`Settings::display_scale`, key `display=auto|1|2|3`, default `auto`): Auto takes the window's scale factor (`devicePixelRatio` in the browser) rounded to the nearest whole number, halves up, 1 to 3 (`display::wanted`: 1.0 and 1.25 give 1, 1.5, 2.0 and 2.25 give 2, 3.0 gives 3); 1x, 2x and 3x are fixed. Either way the factor is lowered until the view keeps at least `MIN_UI` = 640 × 480 (`display::factor`), and the settings row names the factor used when it differs ("3x (2x fits)") and the one Auto picked ("Auto (2x)"). A settings file older than the key loads as Auto. The view is the window's physical size divided by the factor, rounded down; the up to `factor − 1` columns and rows left over at the right and bottom stay black.
- **Why a setting of its own.** The C3 *Interface size* (`scale`, 100 to 300 %) still enlarges only the interface inside the view, for people who want larger controls on any screen, while the battlefield keeps its art size. The display scale answers a different question, how many screen pixels make one picture pixel, and applies to everything. Keeping both keeps C3's accessibility setting as it was; the screen calls the old one *Interface size*, the name *Display scale* now being the new row's.
- **Drawing.** The 2D batch runs in view pixels (`GpuDraw::prepare` gets the view size) and draws through a viewport of the view times the factor (`GpuDraw::set_screen`); the batch reads textures by whole texels, so the viewport enlargement is an exact nearest-neighbour upscale. The battlefield's own target stays the session's view size. The CPU path upscales its frame with `display::upscale` (the local lane checks that both agree: 0 differing interface pixels at 1x and 2x).
- **Input.** Mouse, touch and wheel positions become view pixels in one place, `Display::point` (floor of physical / factor, clamped into the view) and `Display::wheel` (pixel deltas divided by the factor, line deltas unchanged), called from `GameApp::view_point` and the wheel arm; nothing else in the client sees a physical pixel.
- **Run-time changes.** The window layer calls `Client::set_window(physical, scale)` when the graphics start, on `Resized` and on `ScaleFactorChanged` (another monitor, a browser zoom), and the settings row applies at once (`Client::apply_settings` refits). The benchmark keeps factor 1 (`Client::resize`), so its frame sizes mean what they did.
- **Probe.** `?probe=1` also puts `<physical w>x<physical h> <factor> <view w>x<view h> <host scale>` into `data-glasnost-display` on `<body>`.

**Readable text.** Our own interface font and colours, not the spec'd status text or tips:

- Text over the battlefield (captions, chat lines and the line being typed, the network banner, the superweapon countdown rows, whose look S-0512 claim 18 leaves to us, and the failure line) has a one-pixel black outline under its ink at the eight neighbouring offsets (`DrawList::text_outlined`, `Prim::Text::outline`, `colour::OUTLINE`), so it reads over snow as over shadow.
- Dim text (`colour::DIM`) is [160, 166, 176], at least 4.5 : 1 on the backdrop, panel and raised colours (`text_colours_contrast_with_their_backgrounds`).
- A choice box with no label (a table cell of the skirmish setup) gives its value the whole width, so "Closed" and "Random" show whole instead of "Clos..".
- The round capitals C, G, O, Q and S have cut corners and B a short middle bar, at their old widths: S and 5 had the same mask, and O, B and G were hard to tell from 0, 8 and 6 (`every_glyph_is_distinct_and_the_round_capitals_kept_their_width`). No layout moved.
- The status lines (GAME.FNT, S-0213 claim 25) are unchanged: at 2x they are drawn at twice their size like everything else and read well; an outline would change claim 25's look, so none was added.

Tests: `display_tests.rs` (the factor at scale factors 1.0, 1.25, 1.5, 2.0, 2.25 and 3.0 under every setting, the floor at `MIN_UI`, positions, wheel, upscale), `client_display_tests.rs` (a 2x window gives a view of its logical size; a click and a tap at 2x land on their button; the settings row changes the factor at once), `settings_tests.rs` (an older file loads as Auto), `draw.rs`, `paint.rs`, `font.rs` and `widget.rs` tests for the text changes. Local lane: `crates/app/tests/hidpi_lane.rs` writes every screen at 1x and 2x and the GPU frame to `local-lane/side/hidpi/shots/<phase>/` (git-ignored); `web-tests/hidpi.mjs` checks in Chromium at a device scale factor of 2 that the canvas backing, window, factor and view agree, that a click in CSS pixels lands on the base unit, that a 120 CSS-pixel swipe pans 120 view pixels, and that a run-time ratio change is followed. It uses `--force-device-scale-factor`, because under Playwright's emulated `deviceScaleFactor` headless Chromium reports the canvas's device-pixel box at its CSS size.

Known limits: a fractional scale factor gets a whole factor, so at 1.25 the picture is one screen pixel per view pixel (smaller than the desktop's other windows) and at 1.5 two (larger); a fractional factor would blur or unevenly size art pixels. Up to `factor − 1` black columns and rows can show at the right and bottom. The browser's own zoom changes `devicePixelRatio` and so the factor under Auto.

### Performance (M8 C4)

The benchmark (`crates/app/src/game/bench.rs`, our own tooling: nothing in it is game behaviour). It starts a skirmish of our AI houses only on the install's `map`-th offered map, runs `late` ticks straight on the game without drawing, then times frames from fixed views at a fixed size: for each view, `warmup` frames recorded but left out, then `frames` timed ones. The views are found in the game when each starts: **base** (the watched house's densest cluster of buildings), **battle** (the mobile unit with the most units of other player houses in view), **open** (the candidate centre with the fewest objects) and **pan** (a sweep across the map's width through its middle, there and back). Ticks follow the game's own pacer against a virtual 60 frames-a-second clock, so every run and machine ticks on the same frames and draws the same pixels for the same frame; the state hash at the end is printed, and the offscreen host writes a picture of each view's last warmup frame for comparing builds. Maps are known by index and content hash only.

Run lines (DIR is the install folder; nothing of it is copied):

```sh
# Native, in the game window (closes at the end):
cargo run --release -p glasnost-platform-native -- --game --game-dir DIR --bench default
# Native, without a window (also writes one picture per view):
cargo run --release -p glasnost-platform-native -- --game --game-dir DIR --bench default --offscreen
# Firefox: build and serve, open the page at 1920x1080 (a 1080p screen, full screen with F11), click Game folder and pick DIR:
cargo xtask web --release --serve      # then http://127.0.0.1:8000/?mode=game&bench=default
# The browser run, scripted (Playwright; --gpu uses the machine's GPU, without it the browser's software renderer;
# --headed because a headless Firefox may have no WebGL, or only software WebGL):
node web-tests/bench.mjs --install DIR --browser firefox --gpu --headed
```

Check that the summary's `size:` line reads 1920x1080: a display scaled above 100 % can give the page fewer pixels.

The spec is `key=value` words separated by spaces, commas or semicolons (`default` alone means all defaults): `map` (offered-map index, 9), `seed` (7), `players` (AI houses, 2 to 8, 8), `late` (ticks before timing, 9000), `frames` (timed frames per view, 600), `warmup` (60), `views` (`base+battle+open+pan`), `size` (`WxH`, 1920x1080; the window or page uses its own size and the summary says which), `label` (output name; default `native-window`, `native-offscreen` or `web`), `out` (native output folder, `local-lane/m8/c4`), `tick` (`paced` or `every`: a tick every frame), `vsync` (off), `shots` (pictures, on). Natively they go to `out`; on the web they are downloads, and the page's `data-glasnost-bench` turns `done` or `failed` with the summary and rows in `data-glasnost-bench-summary` and `-csv` (`web-tests/bench.mjs` reads those).

On the web the redraws come from the browser's animation frames, whatever `vsync` says, so every frame total is a whole number of display refresh intervals plus timer jitter: a 3 ms frame and a 15 ms frame both read about 16.7 ms on a 60 Hz display, and a 12 ms frame reads 16.7 ms on a 120 Hz one. The web summary therefore replaces the `>16.7ms` column with `missed`: the frames whose total is at least 1.5 refresh intervals, the interval estimated as the median total (the note under the table gives it). `work` there leaves out the GPU work the browser runs later in its GPU process; a forced sync inside `work` is not built (#91).

**Where the time went (this machine, a desktop with a discrete GPU; native offscreen, default spec, 1920x1080; measured on main 63c1df4, before and after on the same game).** Before the fixes every timed frame was over 16.7 ms: the client alone (frame work minus the tick) took 17.6 to 18.4 ms on average. 3. `render::shroud::light_alpha` clips each frame's canvas and the view once and runs its rows as slices, and skips frames that change nothing (all-shroud and all-clear frames); the window keeps the light alpha while the covers and the view are unchanged, and `MapRenderer` uploads the alpha texture only when its values change (light alpha 6.3 to 0.5 ms; uploads 2.1 to 0.6 MB a frame).

#### The tick's cost (M8 C4 part 2)

The tick benchmark (`crates/tools/src/tick_bench.rs`, our own tooling: nothing in it is game behaviour) plays the frame benchmark's game (the same setup through `game::bench::start_headless`: map index, seed, AI houses) without a client, timing every `Game::step` with the host clock. **The fixes (the same game, tick for tick).** Each one does the same work in fewer steps and keeps nothing that is saved, hashed or compared:

- `placement::adjacent` reads the two flags it needs of a building's type (`support_flags`) instead of building the type's whole placement record for every building it meets.
- `Script::place_cell` keeps its answer for each type for the rest of a think (`PlaceMemo`, filled between `Script::begin_think` and `Script::end_think`, which `Brain::think_with` calls; `#[serde(skip)]`, empty outside a think, so a loaded game starts with nothing kept). - A think also keeps `tech::buildable` and `Script::unblocker` by type (and depth), so the tech climb no longer asks the same blocked types again for every army type.

#### The HUD draw list (M8 C4 part 3)

**The cause.** The frame benchmark's "draw list (hud)" lap times `Client::frame()`, and that includes the live radar's picture (`mapview::radar::Radar::rgba`, S-0410), which the session composes again on every frame whose tick changed: every benchmark frame ticks. The drawing of the interface itself takes 0.6 to 0.9 ms of it (most of that the psychic intent lines); the rest was the radar's composition, about 5 to 9 ms a frame. Its largest part was finding each pixel's cell (`minimap::cell_at_pixel`, S-0410 F3, whose divisions run in soft float): about 4.5 ms for the whole picture, against about 0.3 ms for the shroud test. Bisecting with the benchmark (`git bisect --first-parent` from C4 part 1's merge ebbd866 to 8dcc429, bad when the draw list is over 2 ms at tick 9000) gives merge d250715 (the M9 rehearsal's lost starts: a deploy order drops a driving vehicle's path; no crate runs for the yard vehicle), whose parent 3562ebc is good (0.18 ms). That merge changes no client code: it changes the game (its goldens move), and in the benchmark's game after it the watched house has radar at tick 9000 (`econ::radar::available`, S-0410 claim 1), so the radar is composed on every timed frame; before it the house had none, and a radar without it is black and composes nothing. So the cost was always there for a house with radar, and the benchmark started to show it.

**The fix.** The composition must still follow the state on every drawn frame (S-0410), so it is made cheaper, not rarer:

- The radar keeps each pixel's cell, worked out once when it is made (`minimap::pixel_cells`: `cell_at_pixel` for every pixel in row order, with the rules' `quirks.radar_pixel_cell_shift`). The cell of a pixel depends only on the grid, the picture's size and that switch, none of which changes during a game; if the switch read at drawing time differs, the radar composes the plain way.
- `minimap::compose_kept` composes with the kept cells. It shares one body with `minimap::compose` (`compose_by`, which takes the pixel-to-cell lookup), so the friendly gap, shroud and terrain rules have one implementation; `compose` passes `cell_at_pixel` itself and its output is the same as before.
- That body asks for an object's colour (`Arrivals::winner`) only at pixels where some object is listed (S-0410 claim 8: only such a pixel can have a winner), instead of at every pixel.

These are in `crates/deterministic/sim/src/econ/minimap.rs` (the radar's pure composition) and `crates/app/src/mapview/radar.rs`. Nothing kept is saved or hashed: the radar is client state, and the change touches no simulation state, no tick phase and no golden (`cargo xtask gate` passes; `crates/sim-gate` is unchanged).

How drawing was checked unchanged: in the A/B below every run plays the same game (the same state hash at the end), and all 24 view pictures (six runs, four views) are byte-identical (`cmp`); each picture includes the sidebar's radar, with terrain, shroud and objects on it. Every unit gave up (claim 23 row 2: its destination cleared, guard queued).
- **Why they are asked again.** Each of these units is in guard with a target it cannot reach. Guard's processing (S-0215 claim 24) runs the approach step (claim 37), which gives the unit a destination towards its target again; the computation fails, the destination is cleared and the target stays (S-0212 claim 23). The repeats come at the guard processing's rate, not at the retry delay. This is the specified behaviour, so the searches stay.
- **The same question, the same world?** 89 % of all expansions fall in (unit, start, goal, mode) keys asked more than once. But of the 188 failed computations asked again with the same key, 170 expanded a different number of pairs in some search than the previous ask (5 933 against 5 932, say): something in the searched area had changed between the two asks, so the world the search read was not the same, and no cache could have served the earlier answer. That leaves 18 that may have read the same world, and showing that they did would need every outcome input of every cell the search touched. A cache kept across ticks is therefore not built.
- **The cost of one expansion.** A stack-sampling profile (our own, not committed: a scratch program timing these computations again and again on the same world, sampled with `eu-stack`) of the vehicle's computation: the entry outcome is 60 % of the time, and most of it (37 % of the whole) is `occupancy::primary_warhead_flag`, which clones the weapon's name, its warhead's name and the whole warhead record for every candidate cell, to read one flag of the mover's own weapon. **The fixes.** Each one does less work for the same answers; none changes which searches run, in what order, or what they return. Nothing is kept from one path computation to the next.

- **The mover's weapon, read once** (`occupancy`, S-0209 claims 4 and 5). `primary_warhead_flag`, `primary_hits_ground` and `walker_armed` borrow the rules instead of cloning names and records, and `occupancy::Mover` keeps what the outcomes read of its primary weapon (`Primary`: has one, harms walls, harms wood, hits ground) from the first cell that asks; a mover is read once per cell search.
- **The corridor test before the outcome** (`path::counted_search`, S-0212 claim 7). A candidate other than the destination that lies outside the corridor is passed over before its entry outcome is asked: a blocked outcome and an outside candidate both only skip it, and neither question changes anything. The destination's outcome is still asked first, because a blocked destination ends the search from a neighbour (claim 15).
- **One computation, one world** (`path::corridor_search`, `path::SearchScratch`). The cell searches of one computation with the corridor (S-0212 claim 13: up to 5, with retries) all read the world the computation was asked on, which does not change while it runs; they share the start pair and the destination. So the search scratch keeps, for that computation only, each cell's exemption (`corridor::exempt`), each cell's estimate h, and the entry outcome of each step from a search pair in each direction. `corridor_search` starts a computation stamp before its searches and closes it after; a search outside a computation asks everything afresh. The scratch is not saved or hashed, starts empty on load, and a copy of the world starts with empty scratch (`impl Clone for SearchScratch`).

**The fixes.** Each one does less work for the same answers: no answer, order or tick changes, and nothing is kept from one think or tick to the next (no cache crosses a tick; C4 part 2's per-think `PlaceMemo` and `Kept` are unchanged, its adjacency memo is replaced, below).

- **One placement search a type, the cell test first** (`placement::PlaceSearch`, `Script::search_place_cell`; S-0406 claims 3 to 6, 8 and 12). A search reads the type's placement fields once and, for a building, counts the cells that support adjacency (claim 4: the house's and its allies' buildings, the S-0406 F1 rectangle around the foundation less the foundation) with running sums over the spiral's window widened by the adjacency reach, so that a cell's answer is two rectangle counts (the rectangle around the foundation has a supporting cell the foundation does not); a cell outside the window, an upgrade, or a reach over `TABLE_MARGIN` (64 cells, our own bound) is asked the old way. The cell test is asked before the place order's conditions: both only read the world, so either order gives the same answer, and a naval yard's spiral is mostly land, where the cell test fails at once. The free-gap test reads the objects the house knows (its own, and those on cells it has explored), listed once for the search (`Script::known_objects`, `free_among`), not every object for every cell and gap. `cell_test_with`, `explored_with` and `adjacent_by` ask without building lists. `SupportMemo` and `place_legal_kept` (C4 part 2's adjacency memo) are gone.
- **A reveal's discovery compares each cell once** (`shroud::discover`; S-0409 Terms, S-0110 claims 1 and 2). A cell's two cover-piece keys, before and after the reveal, do not depend on which flipped neighbour asks, so each cell is compared once and lists once among the changed cells; the discovered objects are a set, so the order of the changed cells does not matter. A reveal of more than `DENSE_REVEAL` (256, our own bound) cells keeps its cells and the compared cells in grid-sized tables, a smaller one (a unit's sight) in sets, so a sight's reveal does not clear a table of the whole grid. `explored_only_reveal` builds its set of flipped cells at once from the list.
- **The regions' and sectors' rebuild without ordered maps** (`regions::rebuild`, `corridor::build`; S-0212 claims 3, 4 and 13b). The region and sector labels go through a table by union-find root (a root's label is still the count of roots met before it, in the same cell order); the connection pairs go into one list, bucketed by sector and each bucket sorted and merged alone (`merge_met`: one connection per other sector, ordered by it, straight when any of its pairs was); each cell's level, usable-area answer and neighbours are read once for the three levels; `block_of` shifts, the block size being a power of two.
