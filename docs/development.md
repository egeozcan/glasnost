### Simulation crates

Every crate under `crates/deterministic/` is a simulation crate. The checks find them by location, so a new crate placed there is covered automatically. Simulation crates:

- carry their own `[lints]` table (identical across them) instead of the workspace one;
- pick up `crates/deterministic/clippy.toml`, which clippy finds by searching upwards from each crate;
- may depend only on each other and on external crates outside the deny list in `xtask/src/deps.rs`.

## Checks

`cargo xtask check` runs all of the following; each also runs on its own (`cargo xtask deps`, etc.).

### Dependency rule (`deps`)

The `sim` crate (and every other simulation crate) must not depend, directly or transitively, on any non-simulation workspace crate (`render`, `audio`, `net`, `fmt`, `ini`, `convert`, `vfs`, `ui`, `app`, the platform crates, `tools`). It also must not reach graphics, browser bindings, host randomness, hash-seeded maps, threads or clocks (`wgpu`, `winit`, `web-sys`, `getrandom`, `rand`, `ahash`, `rayon`, `tokio`, `chrono`, ...). The check reads `cargo metadata` for every target platform and counts normal and build dependencies. Dev-dependencies don't count. The rule also runs as a unit test in `xtask`, so plain `cargo test` enforces it.

### Determinism (`determinism`, `canary`, clippy)

- **Clippy** bans `f32`/`f64`, `HashMap`/`HashSet`, host-seeded hashers, `Instant`/`SystemTime`, threads and locks, file and network I/O, the environment, and printing macros. It also denies float arithmetic, float comparison, lossy float literals and precision-losing casts. See `crates/deterministic/clippy.toml` and the lint table in each simulation crate's `Cargo.toml`.
- **Float-literal scan.** `let x = 1.5;` uses no float type by name, so clippy alone misses it. `cargo xtask determinism` rejects float literals in simulation code and checks that the simulation lint tables are identical.
- **Canary.** `cargo xtask canary` builds a throwaway crate inside `crates/deterministic/` with one violation per configured entry and requires every expected diagnostic. A misspelt or silently ignored entry fails here instead of letting a float through.
- The narrow float exception from PLAN.md 4.5 (a `Real` wrapper) will be allowed site by site with `#[allow]`, a spec citation and an allowlist entry when a spec requires it.

### Citations (`cite`)

In non-test code of the simulation crates:

- every numeric literal other than `0` and `1`, and
- every `const` and `static` item

must be covered by `// spec: S-xxxx` or `// measure: M-xxxx`. The comment can sit on the same line, or in the comment and attribute block directly above (or opening) an enclosing item, statement, field, variant or match arm. A blank line ends the block.

```rust
// spec: S-0042
const RELOAD_RESETS_ON_MOVE: bool = true;

fn reload_ticks(base: u32) -> u32 {
    base * 15 // measure: M-0007
}
```

- `// nocite: <reason>` in the same places marks a literal that is not behaviour, such as a buffer size of our own design. The reason is required.
- `xtask/citation-allowlist.txt` exempts whole files, again with a reason. It holds the JSONC parser, whose literals are syntax. Stale entries fail the check.
- Every `S-`, `M-` and `Q-` ID mentioned in `crates/**/*.rs` and `data/**/*.jsonc` must exist as a file in `spec/`, `measurements/` or `spec/requests/`, and a cited spec must not be retired.

`spec/` is empty at M0, so the simulation crates hold no behavioural constants yet. Anything that needs one waits for its spec or goes to `spec/requests/`.

### No stock numbers (`stock-guard`)

Stock values can't be recognised without knowing them, and this repository must never know them. So the guard enforces the structure that keeps them out. It covers every file git tracks or would add:

1. **Game-format files** (`.mix`, `.shp`, `.vxl`, `.pal`, `.csf`, `.ini`, `.map`, ... by extension) may only live in fixture directories:
   - In `tests/fixtures/synthetic/` they must match, byte for byte, what our writers generate (`cargo run -p glasnost-tools --bin glasnost-fixtures`), and `FIXTURES.manifest` must be current.
   - In any other `tests/fixtures/` directory they must be text with a `glasnost-synthetic:` line near the top.
2. **Synthetic data** (`data/synthetic/**`) starts with `SPDX-License-Identifier: CC0-1.0`, followed by a `glasnost-synthetic:` line.
3. **Measurements:** nothing under `measurements/local/` is tracked. Records with `value-visibility: local` show no numbers in the value and spread columns of their Result table.
4. **Paths:** no install paths (Steam libraries, Windows program folders, Westwood or EA folders) or home-directory paths in text files. Use `~` or a placeholder. `LOCAL.md` and `.claude/settings.local.json` stay untracked.
5. **Size:** no file over 1 MiB.

Tests that need the user's real install run in a local-only lane (opt-in, never in CI; see "Local-only lane" below); their inputs and outputs are git-ignored. A local comparison of committed synthetic data against the user's imported values needs the converter's (field, value) output. It arrives with the converter in M1 and will run only on the developer's machine.

### Synthetic ruleset

`data/synthetic/ruleset/` is a small, invented ruleset in our JSONC format (CC0). It exercises the format's shape:

- objects keyed by instance name, `inherits` lists and `^abstract` templates;
- `{"+": [...]}` set operations;
- integers in native units, and decimals as quoted strings with a unit.

`crates/deterministic/rules/tests/synthetic_ruleset.rs` checks that every file parses (so every number is an integer), carries the header and is listed in `manifest.jsonc`, and runs the layers through the resolve pipeline: inheritance, set operations, schema 1 (strict, `deny_unknown_fields`), validation, ID interning, the rules hash and `rules explain`. It also checks that `data/schema/ruleset.schema.json`, the JSON Schema generated from the schema types with schemars, is current (`GLASNOST_UPDATE_SCHEMA=1` rewrites it).

### Fixture writers

`glasnost_fmt::fixture` defines `FixtureWriter` (one synthetic file), the registry, the manifest and `check_round_trip` (encode, decode, compare, re-encode). Each format module brings its writers and registers them. `glasnost-fixtures` writes the registry's output to `tests/fixtures/synthetic/`, and the stock guard checks the committed copy byte for byte: after changing a writer, regenerate with `cargo run -p glasnost-tools --bin glasnost-fixtures` and commit the result.

Encrypted MIX fixtures use a key pair of our own (`RsaKeyPair::synthetic`), so they parse only with that key's public half, not with the Westwood key.

### Hostile input and fuzzing

Every parser in `fmt` is panic-free on hostile input: reads are bounds-checked, input-driven arithmetic is checked, allocations are bounded by the input or by `fmt::limits`, and the crate denies `unwrap`, `expect` and `panic` outside tests. `fmt::hostile::run` drives one parser and all its decoders over arbitrary bytes; `ini::hostile::run` reads a document and every stored value in every value form; `rules::hostile::run` parses JSONC, writes it back and resolves it. Two users each:

- `cargo test -p glasnost-fmt --test hostile`, `-p glasnost-ini --test hostile` and `-p glasnost-rules --test hostile` (stable, in CI): synthetic inputs, their prefixes and mutated copies.
- `fuzz/` (cargo-fuzz, nightly, outside the workspace and CI): one target per parser, plus `ini` and `jsonc`; see [fuzz/README.md](../fuzz/README.md).

### Local-only lane

`GLASNOST_GAME_DIR=<install> cargo run --release -p glasnost-tools --bin glasnost-local-lane` mounts a real install and prints counts only: MIX headers decrypted, SHP files and frames (all archives and `conqmd.mix`), VXL files and limbs under `ra2.mix`/`ra2md.mix`, IDX samples, AUD, TMP, PAL, PCX, CSF, HVA and map packs, each by error kind. `cargo test -p glasnost-tools --test local_lane` asserts 100 % on the M1 checks when the variable is set and skips otherwise; CI never sets it. The lane opens only the MIX containers at the top of the folder (`.mix`, `.mmx`, `.yro`); every other file there is counted and never read. It classifies entries with the permissive sniffer (`fmt::sniff`) and counts the strict parsers against that, so a file the sniffer calls SHP but the parser rejects shows up as a failure.

The lane also builds the game's search order (S-0005) and checks the stock outcome (the expansion archive's rules file is the one used, every required archive resolves), imports the rules and art (temperate theater), checks that the result resolves through the rules pipeline, and counts types per kind, the `sim` records of weapons, projectiles, warheads and animations, importer warnings (with the reference-field warnings by kind), art found per kind and coverage outcomes. The binary writes `coverage.csv` (key names and outcomes, no values) to `local-lane/` in the current directory, which git ignores; never commit it.

`cargo test --release -p glasnost-app snapshot -- --ignored` (with the same variable) writes viewer screenshots of a real install to the temp directory, including one of the rules view. Never commit them.

The map lane (M2): the local lane above also decodes every map it finds (`maps decoded (S-0009), no panic`, with importer warnings by kind). `GLASNOST_GAME_DIR=<install> cargo test --release -p glasnost-app --test map_lane -- --nocapture` finds every map by content, loads each with its rules (the map as the map layer), builds its scene, times the build, a CPU redraw of a 1280×720 view and 120 scrolling GPU redraws, counts provisional notes and dropped objects, and writes one screenshot per theater (plus a minimap and a close-up of the first unit) to `local-lane/`. `GLASNOST_MAP_LIMIT=n` limits the maps built, `GLASNOST_MAP_SHOTS=n` the screenshots per theater, and `WGPU_BACKEND=gl` times the GL backend.

### Provisional placeholders

Behaviour that needs a spec stays out of code; where a spec leaves a gap, the code carries an explicit placeholder tied to a spec request (see the table in "Import" below).

Q-0002 is answered by S-0005: `vfs::game` builds the game's search order by name (Table 1), honours loose files for the archives it mounts, finds members by the signed index bisection and mounts the theater and side groups per game. Loose *data* files are an opt-in mod layer (PLAN.md 4.3); with it off, a loose file that would have won is reported and never read. Archives outside the search order (for example the base game's map archives) stay browsable in the viewer but never answer a lookup.

Q-0001 and Q-0003 are answered by S-0103: `render::palette` loads palette files (×4 in 8-bit arithmetic), keeps the theater palettes in force, builds house-colour palettes from colour definitions and picks each object's palette. Shading by light (S-0104) is not applied yet; the viewer shows unshaded palettes.

## Import

The importer turns the user's install into our rules format (PLAN.md 4.3, 4.6):

1. `vfs` mounts the folder for browsing and builds the game's search order (S-0005). Loose data files are an opt-in mod layer (`GameOptions::mod_layer`, off by default, PLAN.md 4.3); with it off, a loose file that would have won is reported and never read.
2. `convert::inputs` resolves the base rules, a language rules file with a valid digest, the game-mode file (the one the user names, or for a skirmish the file of the mode `convert::modes` picks from the mode list: S-0006 claim 13's sections, mode numbers, items, lobby order and remembered-mode rule, `ImportOptions::mode`) and the map; it reports the databases without which the original refuses to start.
3. `ini` reads each file (S-0001 to S-0003) with importer warnings. `ini::Document::layer` gives S-0002's layered load (claims 9 to 12): each line's section and key lookups follow the name-table model (working order, ordered flag, remembered occurrence, peak count and forgetting peaks, `ini::table`), every table starts with nothing remembered (claim 12), lookups after the load answer as the first lookup after it would, and the importer warns about lines that replace or write into a differently named entry or section by a shared hash and about loads that change a table holding a repeated hash. With hash identity off, hashes compare as (hash, name) pairs. No importer path makes a layered load yet (S-0002 claim 6 has only campaign missions use one).
4. `convert::layers` applies the rules layers of one game (S-0004, S-0006): registration in list order with the rank rule for references, sides, tiberiums, per-key layering with its exceptions (S-0006 claims 3 and 5: the "not given" values, and the resets of countries, warheads, particle systems, particles, the difficulty sections and the twelve land-type sections; the `[Powerups]` crate-effect resets and the voxel-animation resets are not applied yet, because no crate or voxel-animation spec reads those values and the crate entries' item form is not specified), colour definitions (S-0103 claim 5) and the colour-adjustment table. A reset is recorded as a reset, not as a value: no reader takes the difficulty sections' repair- and build-delay resets (0.02 and 0.03), whose unit and use S-0006 Constants leave unresolved, so the importer writes no constant for them.
   Types are created by reference as S-0004 claim 13 says, from the tables in `convert::refs` (one per section kind and per game-wide section that names types). A field takes effect when its type reads its section (or its game-wide section is read); single fields are cut to their text limit (127 bytes; 63 for `HoldsWhat`, 31 for `NextParticle` and `SpawnsParticle`, 19 for `AttachedParticleSystem`, or 24 with `long_name_duplicates` off) and list fields create their items in item order; `none` and `<none>` name no type except in the four particle fields of claim 2. Find-only fields (prerequisites, country lists, `ShareSource`, the building superweapon fields, which warn for an unknown name) create nothing. The weapon fields follow claim 13's weapon-slot table, decided by `TurretCount`, `WeaponCount` and `ClearAllWeapons` as the type holds them once the section is read (`art::int_as_of`, the same reading `convert::sim` uses for the slots), in the table's index order. `ToOverlay` and the `Trailer` of aircraft and projectiles are read from an art section while the type reads its rules section (claim 14): for buildings and aircraft the one named by the image in force at that read, with the snow suffix of S-0007 claims 9 and 10 (`art::ImageWalk`, shared with the art lookup; no suffix for voxel aircraft); for projectiles only the one named by that read's non-empty rules `Image`, unsuffixed, with no fallback to the type name. Animation fields come from the animation's art section. New types fall into the rows of claim 4: `[AI]` then `[General]` before the passes (read in the layer), the passes in rank order (a new type is read in the layer if its kind's rank is at least the creating pass's), then `[CrateRules]` (wood crate, crate, water crate), `[CombatDamage]`, `[Radiation]`, `[AudioVisual]` (`Smoke` read for two fields) and `[SpecialWeapons]`, the second reading of every warhead in a layer with `[SpecialWeapons]` (row 5) and the tiberium list (row 6), none of which are read in the layer. With `unlisted_reference_unread` off, every type created by reference reads the creating layer. After the last layer, `GasCloudSys` is created if missing (claim 3); it reads no section. Within one section, keys that create types of one kind take effect in the order of the `convert::refs` tables (claim 4 leaves that order to us). A long name (claim 8) that would make a type of its own kind create copies of itself without end is stopped (claim 15, a departure, no switch): a reference requesting a kind and name, compared without regard to case, already used to create the referring type or an ancestor in this layer creates nothing, with a warning. Numbered weapon fields above 18 register weapons up to `WeaponCount` (claim 16); only the first 18 fill slots (S-0308). Two creations after the rules layers are not implemented, so `terrain_objects` and `animations` stay listed in the import record's `incomplete_registries`: the terrain objects a map's placements name and the animations the theater control file's tile animations name (S-0004 claim 3).
5. `convert::art` looks up every type's art for one theater (S-0007), with the game's per-game archives mounted. A building's eight other sprites follow claim 11's later-read table (a read whose art section does not set a name, or sets it empty, keeps the sprite). Weapons, warheads and tiberiums have no art files of their own (claim 32). Not implemented yet, because nothing draws them before M6: the art of projectiles, particles, particle systems and voxel animations (claims 26 to 30), and the superweapon sidebar icon (claim 31).
6. `convert::emit` writes a schema-1 tree: names are byte-exact (bytes 128 to 255 map to U+F780 to U+F7FF), keys no spec maps yet stay as INI text, values the layering computes (light values in thousandths, S-0104 claim 12) replace their text (`derived`, `ini_globals_derived`), and every value carries its INI history for `rules explain`. Import errors cover the conditions under which the original would not start, and loose names that differ only in letter case (S-0005 Edge cases).
7. `convert::sim` writes the typed `sim` section (`rules::sim`): the simulation fields of the rules and art data, each written only when the layered data gives it, folded over its history (values a form cannot read and "not given" values keep the held value), with decimals as text in our grammar that reads as S-0003 reads the stored text (a test cross-checks `num::decimal` against `ini::value::decimal`). Land-type rows are the layered values of the twelve land-type sections, whose omitted keys the layering resets (S-0211 claim 2, S-0006 claim 5, `quirks.override_resets_keys`), the anti-air rate follows S-0215 claim 21, locomotion classes S-0211 claim 3, the locomotor field S-0207 claim 14 (a class identifier of table T3; another form or an unknown identifier keeps the locomotor in force, with a warning), and the art fields (infantry sequences, fire frames, `Crawls`, building foundations, overlay `has_art`, an overlay's `DamageLevels` from its image section, S-0210 claim 13) are rebuilt once the art lookup has run. Animation types take the fields their creation draws read from their art sections (`RandomRate`, the bouncing flags, the chain reaction and the middle-event effects with `SpawnsParticle` and `NumParticles`, S-0109 and S-0202 Import mapping, and μ from the art lookup, S-0109 claim 25); particle types take `BehavesLike`, `MaxEC` (a zero value warns unless the behaviour is railgun), the colour count of the last section's `ColorList` and the starting colours (S-0202 Import mapping). Type-name lists and references (a type's `Owner`, `[General] BaseUnit`, the gate and wall tower types of S-0112, an overlay's cell animation `CellAnim`, S-0009 claim 12, whose `none` and `<none>` clear it) are resolved to type keys by S-0003 claim 14's comparison, unknown names dropped with a warning; an overlay's `has_art` is "artwork or a cell animation" (S-0009 claim 12); the game's tech level (`[MultiplayerDialogSettings] TechLevel`), the maximum player count of the unused-house cleanup (`[Maximums] Players`, S-0009 claim 28) and the early phase's passive field (`multiplay_passive_base`, S-0009 claim 33) take the base rules' value only. A terrain type's `Strength` follows S-0102 claim 23: unset until a layer gives it, after each layer holding its section an unset strength takes `[General] TreeStrength` as it stands then (25 when absent), −1 unsets it (`quirks.tree_strength_fixed_at_first_section`); a type left unset is written without a strength, which the simulation reads as −1 (S-0009 claim 42).
   The combat fields (M4, `convert::sim::combat`, S-0301 to S-0315) follow each combat spec's Import mapping: weapons (rate of fire, burst, speed, the lepton-form ranges as decimal text, the effect and choice flags), projectiles (flags, acceleration, arm time, cluster, art `Voxel`, and `Trailer` and `SpawnDelay` from the art section of each read's non-empty rules `Image`, S-0007 claim 33; the rules keys have no effect), warheads (`Verses` as eleven exact decimal expansions of S-0003 claim 13's doubles, spread, falloff, the damage rows, debris), the shared `combat` record of infantry, vehicle, aircraft and building types (armour class by S-0305's words, ammunition and reload, immunities, debris and death fields, targeting flags, the five threat coefficients, art muzzle positions and turret offset), the weapon slots of S-0308 claim 1 (both forms, with the clear-weapons flag applied at each reading of the section), the vehicle burst delays and firing frames, the building art fields (aim shift, height, voxel turret, pixel offsets, delayed fire), country factors and veteran lists, the building `Cost` (S-0311 F1, S-0314 claim 5), the three difficulty rows (`sim.difficulty`) and the game-wide combat values. Weapon `Speed`, the ranges, `AirRangeBonus`, `BallisticScatter` and `FireSupress` given as −1 count as not given. Type names in the new fields resolve to type keys where a type of that name exists and keep the name as written otherwise (a field S-0004 claim 13 does not list as creating, or a name that claim 8 duplicates); every registered weapon, projectile, warhead and animation gets a `sim` record, empty for one that read no section (it keeps the engine defaults of its kind); fields the schema documents as type keys (veteran lists, `HarvesterUnit`, the crew types) drop unknown names with a warning. The importer warns for the bad-data cases of the combat specs' Edge cases. `Decimal::value` reads text at 24 bits (S-0003 claim 6), so a versus value that is not exactly a single needs a 53-bit reading of its text (`num::decimal::nearest_double`) to recover the double.
8. `rules::resolve_ruleset` applies mod patch layers, inheritance and set operations (only in our own collections, never inside imported INI data), types, validates, interns IDs and hashes.

Every quirk switch of the implemented specs has a field in `ini::Quirks` (including S-0003's `percent_list_integer_prefix` and `list_items_untrimmed`, the latter shared by S-0303, S-0311 and S-0312 list items), `vfs::GameQuirks`, `convert::layers::LayerQuirks`, `convert::art::ArtQuirks`, `convert::sim::SimQuirks` (S-0308's `clear_weapons_any_turret_count`, S-0309's `coefficient_zero_replaced`, S-0102's `tree_strength_fixed_at_first_section`), `convert::theater::TheaterQuirks`, `convert::map::MapQuirks` or `render::palette::PaletteQuirks`, defaulting to the original's behaviour; the import records them under `import.quirks`. The renderer's and the map viewer's switches are fields of `render::projection::ProjectionQuirks` (S-0101), `render::compose::ComposeQuirks` (S-0102 compositing), `render::light::LightQuirks` (S-0104), `render::voxel::VoxelQuirks` (S-0105), `render::overlay::OverlayQuirks` (S-0112), `render::palette::PaletteQuirks` (S-0103), `render::shroud::ShroudQuirks` (S-0110) and `app::mapview::quirks::ViewQuirks` (S-0102 draw order and placement, S-0108 building frames), each with `named()`. `rules::quirks::tests::every_spec_quirk_has_a_switch` checks that every switch the simulation specs, S-0006, S-0009, S-0010 and S-0107 name is a field of `rules::Quirks` or listed with its owner in `EXTERNAL_QUIRKS`; `app::mapview::quirks::tests::every_rendering_spec_quirk_has_a_switch` checks that every switch `spec/rendering/S-01*.md` names is a field of one of the structs above (or of `rules::Quirks`, `LayerQuirks`, `ArtQuirks` or `SimQuirks`) or is listed in `app::mapview::quirks::NOT_IMPLEMENTED` with its reason (the table below). Two S-0009 switches of `MapQuirks` are not consulted yet, because our engine has no lobby and draws no preview markers: `lobby_counts_zero_waypoint` and `preview_markers_from_header`. ## Simulation (M3)

`glasnost-sim` runs the game rules on the typed ruleset and map. Everything in it is integers and the soft-float types of `glasnost-num` (S-0205: IEEE binary32/64 in integers, round toward zero under `quirks.chop_rounding`), with ordered containers only.

- **Rules and data.** `rules::SimRules` is built from a resolved ruleset (`SimRules::new(&resolved.ruleset, &resolved.sim_rules_hash)`): typed per-kind tables, the 418 quirk switches of `rules::Quirks` (every one defaulting to the original; `refused_death_keeps_unit` of S-0107 claim 17 is not consulted, since M3 has no death handling), and engine defaults cited to their specs. ## Simulation (M4: combat)

Combat lives in `glasnost_sim::combat`, driven from the tick pipeline and the behaviours of M3; every phase runs in S-0203's places (no component picks its own order). Its rules are typed in `combat::data` (`CombatRules`, built inside `SimRules` from the schema's combat fields: weapons, projectiles, warheads with their versus values read at double precision, per-type `TypeCombat`, countries' multipliers, the general values and the difficulty rows). The quirk switches the combat specs name are in `rules::Quirks` (236 switches now, each defaulting to the original), plus `clear_weapons_any_turret_count` and `coefficient_zero_replaced` (importer, `convert::sim::SimQuirks`) and `percent_list_integer_prefix` (`ini::Quirks`); the quirk inventory test checks every switch the simulation, movement, infantry, rendering and combat specs propose.

- **Firing (S-0301, S-0310, S-0313).** `check` is the firing check in S-0301 claim 9's rank order, with S-0310's aiming answers (turret and body facing, the building aim point); `fire` makes a shot (burst counter, the delay kinds and their draws, ammunition and reloading, firing-frame sync, the full delay F1 and the reload F3), `position` the fire point (the 3 × 4 single-precision matrices of S-0313 F1, burst alternation, building pixel shifts F3), `behave` the firing parts of the behaviours (vehicles S-0310 claim 9, infantry S-0107 claim 11, buildings S-0215 claim 32 with the turret snap), and `ballistics` the arc speed and reachability.
- **Weapons and acquisition (S-0308, S-0309).** `weapon` chooses the slot by table P (with table N, gattling and switching types, elite slots), the mean damage of a healer for acquisition and the versus lookup (S-0304, S-0305); `acquire` holds the searches (ring order F2, candidates by table C, threat F4 to F9, early stops, the timer draw first), retaliation, anger, expected remaining health and the per-tick search after an actor's processing, area guard and hunt.
- **Projectiles (S-0306, S-0307).** `projectile` launches (straight and arcing pitch, scatter F5), flies (turning F7, steering F10 to F12, the rows of tables T1 and T2), detonates (detonation point, cluster draws, airburst children) and removes shots; projectiles are kept in `World::projectiles` in update order, with IDs from the object counter. `range` is the range test (elevation bonus F2, measured and source points, the high-bridge refusals) and `lof` the line-of-fire walk.

## Simulation (M6b: depot cycle)

The depot cycle of S-0314 claims 6 and 16 to 24, S-0504 claims 7, 8, 12 and 14 and S-0215 claim 29 is built in `glasnost_sim::depot`. A repair depot (a building with `UnitRepair=yes`) and a naval yard with the repair flag accept an allied vehicle, which drives to the docking point, docks, and is repaired in three phases until the depot sends it away. The ledger is [docs/m6-claims/depot-cycle.md](m6-claims/depot-cycle.md); the tests are in `crates/deterministic/sim/tests/claims_s0314_depot.rs` and `claim_14_*` in `claims_s0504.rs`.

- **State.** `Object::depot` (`depot::DepotState`): a vehicle's `link` (depot, place, tethered; valid only while its contact is that depot), `queued` (claim 23's queued entry) and `loco_off` (claims 21 and 22); a depot's `serviced` vehicle. The phase is the depot's *repair* progress count. This state came with save format 18.
- **Permission and entry (claims 16 and 17; S-0214 table V value *n*).** `depot::accepts` is claim 16's permission. `targeting` gives *enter* over an accepting allied depot (row n3) and *no-enter* for a vehicle of zone *fly* (row n1); a held one-place depot keeps *select* (row n4). The enter order takes contact at once in the first free place (`depot::order_entered`). The vehicle's *enter* processing (`depot::process_enter`, from `process`) repeats the request; only a depot with the pad flag tethers it there (`depot::pad_exchange`: the foundation centre's cell, and no moving destination or place 0 more than 128 leptons from the centre), and a tethered vehicle turns to 16384 and, once still, queues *repair* with the ready mark on the depot and *sleep* on the vehicle. Reaching the docking-point cell during movement (`depot::movement_arrival`, from the driving and hovering locomotors' arrivals) queues *repair* and *sleep* without a tether, so an ordinary depot repairs its vehicle untethered. An unarmed depot's guard processing makes the early start of claim 17 (`depot::early_start`, from `combat::behave`).
- **Docking point (claim 18; S-0504 claim 12).** `depot::docking_point`: the foundation centre plus the place's displacement (`econ::release::pad_position_at`, S-0404 claim 15's rules), or the cell (2, 1) for a vehicle factory. `path::heading_point` heads a vehicle in depot contact for it, and `hover::destination_point` makes it a hovering vehicle's destination *D*, so a hover stops in the docking cell of a depot larger than one cell.
- **Repair (claim 6; S-0504 claim 8).** `depot::process_repair`: waiting (the naval waiting gate, 3 ticks to settling), settling (one step; locomotor off only within 200 leptons; moving farther away, no step, the locomotor switched on and *D* ticks; not needed sends it away unannounced), working (*D* + *K*<sub>u</sub> − 1, then *K*<sub>u</sub>; done or not needed announces and sends it away; cannot pay returns to settling and announces low funds at exactly 0 credits). Release goes to the depot's rally point, else claim 25's departure cell (`depot::exit_cell`: door kinds, the naval rows, S-0404's exit list or the perimeter, the first giving free); a neutral or special house's vehicle with a guard spot goes there. With no cell the vehicle keeps contact: from working it returns to settling with a 1-tick retry, in settling it retries after *D*. The announcements are `Sound::UnitRepaired` (audio: F7 kind *unit repaired*, 2 cells, 400 ticks) and `Sound::LowFunds`, the depot owner's only.
- **Orders, sale, destruction, power (claims 20 to 23).** `depot::order_applied` (from `orders::apply_behaviour`) and `depot::stop_order` give claim 20's and claim 23's order rules; a docked vehicle is tethered (`econ::tethered`) and keeps its contact, while an untethered one, at an ordinary depot in any repair phase, is released by another order. `depot::vehicle_turn` (from `tick::object_turn`, after the locomotor movement) retries a queued entry every tick; permission queues *enter* with an immediate start only when ready. A sale gives the run-away notice (`depot::sale_started`, from `econ::sell`) and releases contacts at the next selling processing; destruction releases without notice (`depot::depot_destroyed`, from `combat::death`, beyond S-0312 claim 17's kill distance). A switched-off depot refuses new acceptance only. The three quirks of S-0314 Edge cases are live.
- **Hover stranding.** `depot::locomotor_off` is read by the hovering locomotor of S-0503 (`hover::tick` does not travel while it holds): a hovering vehicle is stranded after its depot is sold or destroyed (`quirks.depot_loss_strands_hover`); no other locomotor reads it.
- **Import.** `UnitRepair`, `NumberOfDocks`, `DockingOffset`*i* and the factory kind were already imported. New: an importer warning for `NumberOfDocks` above 1 on a repair depot (S-0314 Edge cases).
- **Our AI.** At each think, a damaged idle army vehicle (at or below half its strength, our tuning) of a house with an accepting depot is given an ordinary enter order on the nearest one (`Brain::send_for_repair`; S-0314 claim 24).
- **What play needs.** A repair depot is a building type with `UnitRepair=yes`; built and placed like any building, or spawned by a map. Its foundation cells must let the vehicle reach the docking point: S-0209 claim 5's row VP12 makes cells beyond `NumberImpassableRows` passable. ## Own AI (M5b)

`glasnost_ai::game::Game` runs every game with AI houses: the world plus one `brain::Brain` per AI house of the setup (`HouseSetup.ai` and the player role, glossary *AI house*). In each tick, after the person's orders, every AI house that is not defeated or removed thinks and its orders go through `orders::issue` like a person's; then `tick::step` runs. The brains are saved with the game (`Game::save`, `Game::load`) and hashed with the world (`Game::state_hash`), and a replay holds only the setup and the person's orders: `Game::run_replay` runs the AI again. The AI draws from no random stream.

The brain plays in two layers (PLAN §4.7 stage 1 and enough of stage 2):

- **The plan** (`scripted::Script`, M5a's scripted builder), every `THINK_PERIOD` ticks: deploy the MCV, build power, a refinery and factories, keep two harvesters, build the army round-robin and attack in waves (see `scripted.rs`). It rebuilds lost power, refineries, factories and harvesters, since it asks for each role whenever the house has none (fewer harvesters than the plan's).
- **Selling out** (part of the plan's think): a house whose harvesters' summed loads and credits show no income for `BROKE_PATIENCE` ticks (a rise within `SALE_WINDOW` ticks of its own sale counts as the refund) and that cannot afford anything it could build sells its costliest sellable building (`sell::sellable`, S-0408 claim 3), one per patience period, keeping one factory per kind while it has army units, and from then on builds no buildings, harvesters or construction yard, only army units. Income ends the mode. A house with nothing left to fight with thus sells out, so a game between two broke houses ends. The loads of its slaves on the map count with the harvesters', so a house whose slaves are delivering is not broke.
- **The reactions**, every tick (no reaction delay): place a finished building at once; defend the base (every army unit within 30 cells of home that is not already fighting one attacks the nearest seen enemy within 12 cells of a house building); rebuild a lost construction yard (build the cheapest buildable unit that deploys into one, queued behind what the line holds); and move an idle deploying unit that could not deploy where it stands to the nearest spiral cell where the deploy's cell test (S-0415 claim 3, the answer a person's deploy cursor gives) passes.

- **New units (M6a).** Aircraft are army of their own kind in the round-robin; a type the house cannot build yet makes the tech climb build its blocker, so a pad for an aircraft and a naval yard for a ship (ordered only when the placement spiral has a cell for it, which for a yard means water). An idle aircraft with ammunition attacks the nearest seen enemy it can hit and flies back to rearm by itself (S-0501); aircraft are kept out of the land waves. A launcher that spawns rockets (S-0506) is army like any armed vehicle. A unit whose goal lies outside its reach region (`Script::reachable`, S-0212 claim 4: a ship for a goal on land) goes to the nearest cell of its own region instead, as a person sends ships to the water off an enemy base. Defence and attacks pick only targets one of the unit's weapons can hit (`scripted::can_attack`: `weapon::would_use` gives a weapon and the firing check answers neither *illegal* nor *impossible*), so ground units do not chase hovering aircraft.

What it knows is what a person in its seat knows: its own objects, its production lines and sidebar offer, enemy objects on cells its house has explored (`econ::shroud::explored`; fog of war is off in a skirmish, S-0409 claim 19, so a person sees what stands there), the map's start waypoints (lobby knowledge), and the answers of order-legality checks a person's cursor gives (`placement::place_legal`, `placement::cell_test`). Its placement spacing (`Script::free`) counts only its own objects and those on explored cells. A refinery is a building with the refinery flag or a member of the refinery group (S-0407 Import mapping, `PROC`); a role the house cannot build a type for yet does not hold up the next one, and the army waits for harvesters only while a harvester type is buildable, or a vehicle factory is while the house has none. Refused orders are not an error: the next think tries again. Every number in `brain.rs` and `scripted.rs` is tuning of our own opponent (`nocite`), not game behaviour. Types are found by role from the rules among those the house can build, so every faction plays with its own types. A slave miner (S-0402 claim 14) plays the harvester role and its deployed building counts towards the harvesters kept; it is built without a refinery, and a resting one whose slaves are home is sent to harvest with the nearest explored resource cell as its destination, the order a person gives it (no other order starts a player house's slave miner); it then finds its site and deploys by S-0402 claim 22. A slave with a master is never army, even when its type is armed. Only a vehicle that deploys into a construction yard is deployed as the MCV or kept as the lost yard's replacement.

Tests: `crates/deterministic/ai/tests/ai.rs` on the synthetic skirmish (`fixture`): the build-up, a rebuilt power plant, base defence, and shroud honesty (two worlds that differ only by an enemy unit on a cell the house has not explored give identical orders over a think period) in debug; a broke house selling a building (and a house with income not selling), the rebuilt harvesters, the rebuilt construction yard, a slave-miner side earning income from its slaves (and rebuilding a lost slave miner) and two whole games played to one winner with each house's loop checked in release (`cargo test --release -p glasnost-ai -- --include-ignored`). The determinism gate adds three AI duels (`duel`, `duel-diagonal`, `duel-naval`: the AI against itself on `fixture::map`, `fixture::map_diagonal` and the water map `fixture::map_naval`, hashed with `Game::state_hash`, saved and loaded halfway and at the first tick with a rocket in flight and with an aircraft in the air; the loaded game must hash alike and the run goes on from it, and a full run of the straight duel must have flown both; the diagonal game ends before a launcher is sent, and since S-0507 revision 4 the naval game no longer reaches a launcher shot within its run). The fixture (M6a) adds a pad, an armed plane, a V3-style launcher with its set-A rocket type (not scored, S-0414 claim 4), a naval yard and a gunboat, its own tile catalogue (`fixture::catalogue`, water tile `fixture::WATER_TILE`) and the release tests `flies_aircraft_from_pads` and `builds_a_navy_on_a_water_map` in `tests/skirmish.rs`. ## Audio (M5b)

`glasnost-audio` turns what the game reports into sound, following S-0701 (sound selection, revision 3). It never feeds back into the simulation, and nothing in it is simulation state. The claim 29 test checks that a game's state hash is the same with and without audio.

- **Samples (`bank`).** `SoundBank` maps names (case-insensitive) to samples and decodes each one on first use (`clip`), caching the result. A name that does not decode is remembered as a failure. Sources: IDX/BAG banks (`add_idx`), AUD and plain PCM WAVE files (`add_file`, with WAVE read by `glasnost_fmt::pcm::Pcm::from_wav`), and decoded PCM (`add_pcm`). `bank::discover(&Vfs)` builds the one sample bank of S-0701 claim 34 from `AUDIO.IDX` and `AUDIO.BAG`, each found through the game's file lookup (S-0005), so either may be an archive member or a loose file. It returns a `DiscoverReport` (index found, index without a readable data file, sample count). Sound entries play only bank samples.
- **Sound entries (`catalog`).** `SoundCatalog::from_ini` reads the sound database (S-0701 claims 1 to 3): samples, control and placement words (the last of `shroud` and `unshroud` applies), levels (F1, and with `quirks.full_volume_16383` off an entry of 100 or more is at full), priority, limit, range, delay, pitch shift and attack/decay. The install reads the sound and speech databases (S-0005 Import mapping) into `Install::sounds` and `Install::speech`. The client builds the catalogs at each game start, under that game's quirk switches.
- **Announcement entries (`speech`).** `SpeechCatalog::from_ini` reads the speech database (claim 26). `Announcer` keeps one line playing at a time and queues the others by priority (claim 27). Each announcement requests a fixed entry (`Announcement::entry`, S-0701 Import mapping), and the sample is chosen by the local house's voice set. Announcement samples are separate files, the eight-character name plus `.wav` (`speech::file_name`, claim 34), never bank samples. The client's start job reads the local voice set's files (`SpeechCatalog::files`) through the file lookup and hands them to `Audio::set_voices`. Announcements skip the master level and the sound volume option (claim 35); our engine has no options screen, so the voice option stays at full.
- **Names by role (`names`).** `SoundNames::from_ruleset` reads the sound keys the specs name from the imported rules: the per-type keys (S-0701 Import mapping, S-0415, S-0107, S-0210, S-0207, S-0214), the weapon reports, the animations' start sounds (S-0109 claim 13) and the game-wide keys (S-0408, S-0410 claim 3, S-0416 claim 4, S-0701). Lists follow S-0003 claim 12 and `quirks.list_items_untrimmed`.
- **Mixer (`mixer`).** `Mixer` is integer only and mixes interleaved stereo at the output rate. It provides:
  - placement on screen in half-pixels (F2), levels and truncation (F3), and attenuation and balance (F4);
  - 16 channels and a pool of 300 instances, of which 200 may follow an object; the per-entry limit (claim 8) and the victim choice (claim 9);
  - the per-instance draws in their order: pitch, shift, pre-delay, attack/body/decay, the startup draw, the shuffle (claims 10 to 14);
  - loops and the dormant restart (claim 15);
  - a separate announcement voice;
  - `render`, which tests call offline with no device.
- **Outputs (`output`, `web`, `pipe`).** `Output::pump` is called once per frame and pushes enough mixed audio to stay about 0.1 s ahead.
  - **wasm32:** `web::WebOutput` schedules 1024-frame AudioBuffers on an AudioContext. The context starts suspended and is resumed by the first pointer, key or touch gesture. `Audio::resume` can also be called from an input handler.
  - **Native:** the `native-output` feature (off by default) pipes 16-bit stereo to `pw-cat`, `pacat` or `aplay`. This is a stopgap: an in-process device crate (cpal) could not be fetched offline when M5b was written, and the default build needs no system audio headers.
  - **Otherwise:** `NullOutput`, which discards voices, is used and its state names the reason.
- **Events (`Audio`).** The game client owns one `Audio` (`Audio::platform()` picks the output). At each game start it calls `set_quirks`, `set_catalog`, `set_speech`, `set_bank`, `set_voices`, `set_names` and `start(world, local_house)`. Then it calls:
  - after each tick, `tick(world, effects, unsync)`. This plays:
    - the hit, shot, death and animation effects (claims 20 to 22), and the game-wide building damage and death sounds for building types with none of their own (claim 37);
    - the response slots (claim 16);
    - the movement, turret, unit-ready, building and promotion sounds (claim 23), and the promotion announcement (claim 36);
    - the low-funds, low-power, base-attack and unit-lost announcements (claim 28, F7).
  - after input:
    - `selected` for the first object each input selects (claim 17);
    - `ordered` for a click that gave orders (claim 18, F6). The repair vehicle (`FV`) repairing plays the repair response; an attack with a secondary weapon by a non-elite object plays its secondary-weapon response;
    - `key` for the guard, stop and scatter commands (claim 19);
    - `cue(UiCue)` for the interface sounds (claim 24, S-0410 claim 3, S-0416 claim 4) and the building placement sound. Under claim 24 the start, queue, resume, hold and cancel clicks play the build click with their announcement (start and resume request the training entry for infantry and the building entry for any other kind; a queued copy on an already active line requests no announcement). A busy production line gives only the unable-to-comply announcement, and a refused placement click only the cannot-deploy-here announcement. A page request already at the strip's end plays the refusal sound, an accepted page move the tab sound, and nothing plays while the icons fit (S-0411 claim 18).
  - every frame, `set_view` (the view's origin and size, with S-0101's projection) and `frame(now_ms, unsync)`, which runs the audio passes and pumps the output.

  Game-side choices and the mixer's per-instance draws all take raw values from the client's one unsynchronised stream (S-0202 claim 11, S-0701 claim 30). `frame` and `service` lend that stream to the mixer for the pass and take it back. `now_ms` is host time; S-0701 revision 14 claim 30 (answering Q-0671) specifies the deterministic logical schedule that replaces it, which is not built yet (row below).

## Game client (M5b)

A person plays a skirmish against our AI from the main menu to the end screen, natively (`cargo run -p glasnost-platform-native -- --game --game-dir DIR`) and on the web (`?mode=game`, docs/web.md). The interface is our own code, `glasnost-ui` (no egui), drawn by `glasnost_render::batch2d` within the WebGL2 core.

- **Screens (`glasnost_ui::shell`).** Main menu, then skirmish setup (S-0412), then the game, then the end screen (S-0414), then back to the menu. The setup offers every multiplayer map with at least two start positions (S-0009 claim 23, `install::start_count`). Maps are known by their position in the list and, in the game, by a content hash (`session::content_hash`), never by a stock name. Lobby colours are the colour slots of S-0103 claim 10.
- **Modules (`crates/app/src/game`).**
  - `install` reads what the menus need from the mounted install: the base rules (setup values, S-0412 Import mapping), the maps and their start counts, the sound names, the sound and speech databases and the sample bank.
  - `play` is the running game without drawing: selection, tools (select, place, sell, repair, power), sidebar clicks (`econ::sidebar::click`), status messages and the end screen. Every order goes through `glasnost_ai::game::Game::issue`, so it is in the replay.
  - `session` is a game on a loaded map: camera (S-0101 limits), the live scene, radar, gestures, and the HUD's draw list.
  - `paint` turns draw lists into batch quads, and draws them on the CPU for tests.
  - `client` holds the screens, jobs, pacing, sound and input, without a window.
  - `window` runs winit and wgpu. The battlefield is drawn on the GPU (`map_gpu::MapRenderer` into a target the batch shows through `Batch2d::set_image_view`); if that fails, it falls back to the CPU compose.
- **Pacing.** `mapview::live::Pacer` gives one tick per drawn frame at most, measured from each cycle's start (S-0201 claims 2 to 4). Nothing ticks while the options menu is open (claim 8) or the window is out of focus (claim 9). The speed comes from the setup and the options menu.
- **Sound.** `Audio` is created at the first game start and resumed on the first gesture. At each game start the client sets it up from the install's sound and speech databases, bank and names, under the game's quirk switches (S-0701). After each tick it calls `tick`. After input it calls `selected`, `ordered`, `key` and `cue`, with what `play` collected in `selected`, `acks`, `keys` and `cues`. Each frame it calls `set_view` and `frame`. Game-side choices use the unsynchronised stream seeded with the game's seed (S-0202 claim 8).
- **Input.** Clicks go through `glasnost_sim::targeting` (S-0214). A left release selects or orders (claim 26), a left drag is the band box, a right release clears the selection or ends a sidebar or placement mode (claims 26 and 28), and a right drag past F8 (8 pixels on either axis, `band::RightDrag`) scrolls the view (S-0101 claims 16 and 17) and is released with no effect (claim 27). The key commands are S-0213 table T2. Box selection, scrolling and key bindings follow those claims; the client's remaining interim rules are in the table below.
- **Tests.**
  - `game::play` tests: select, move, deploy, build and place, box selection, and surrender to an end screen, all on the synthetic skirmish.
  - `game::client` tests: menu, setup and the start job on a synthetic install.
  - `game::paint` tests and `crates/render/tests/offscreen_batch2d.rs`: the batch's pixels against the CPU reference, image views included.
  - The local lane: `GLASNOST_GAME_DIR=<install> cargo test -p glasnost-app --test ui_lane -- --ignored --nocapture` drives the client from the menu through a game (deploy, a few hundred ticks, a building ready for placement, surrender) to the end screen. It writes `menu.png`, `setup.png`, `game.png`, `placement.png` and `end.png` to `local-lane/ui/` (git-ignored; never commit them). With a GPU adapter it also draws the game frame through the window's path (`game::GpuDraw`) offscreen, to `game-gpu.png`, and compares it with the CPU frame. It writes the first icon's palette indices as grey levels to `icon-indices.png`, which separates the icon palette (Q-0275) from the decoding. `GLASNOST_UI_MAP=n` picks the n-th offered map and `GLASNOST_UI_TICKS=n` sets the ticks before `game.png`.

## Tests

```sh
cargo test --workspace          # unit tests, render tests, dependency rule
cargo xtask check               # the checks above
```

`crates/render/tests/offscreen_quad.rs` renders the palette quad on a real or software GPU and compares every pixel with the CPU palette lookup. Without an adapter it skips, unless `GLASNOST_REQUIRE_GPU=1` is set (CI sets it and installs lavapipe). `WGPU_BACKEND=gl` runs it on the native GL backend. `crates/render/tests/webgl2_shaders.rs` translates every shader to GLSL ES 3.00, so constructs WebGL2 can't express fail without a browser.

The browser lane is described in [web.md](web.md).

## CI
