### Simulation crates

Every crate under `crates/deterministic/` is a simulation crate. The checks find them by location, so a new crate placed there is covered automatically. Simulation crates:

- carry their own `[lints]` table (identical across them) instead of the workspace one;
- pick up `crates/deterministic/clippy.toml`, which clippy finds by searching upwards from each crate;
- may depend only on each other and on external crates outside the deny list in `xtask/src/deps.rs`.

## Checks

`cargo xtask check` runs all of the following; each also runs on its own (`cargo xtask deps`, etc.).

### Dependency rule (`deps`)

The `sim` crate (and every other simulation crate) must not depend, directly or transitively, on any non-simulation workspace crate (`render`, `audio`, `net`, `fmt`, `ini`, `convert`, `vfs`, `ui`, `app`, the platform crates, `tools`). It also must not reach graphics, browser bindings, host randomness, hash-seeded maps, threads or clocks (`wgpu`, `winit`, `web-sys`, `getrandom`, `rand`, `ahash`, `rayon`, `tokio`, `chrono`, ...). The check reads `cargo metadata` for every target platform and counts normal and build dependencies. Dev-dependencies don't count. The rule also runs as a unit test in `xtask`, so plain `cargo test` enforces it.

### Determinism (`determinism`, `canary`, clippy)

- **Clippy** bans `f32`/`f64`, `HashMap`/`HashSet`, host-seeded hashers, `Instant`/`SystemTime`, threads and locks, file and network I/O, the environment, and printing macros. It also denies float arithmetic, float comparison, lossy float literals and precision-losing casts. See `crates/deterministic/clippy.toml` and the lint table in each simulation crate's `Cargo.toml`.
- **Float-literal scan.** `let x = 1.5;` uses no float type by name, so clippy alone misses it. `cargo xtask determinism` rejects float literals in simulation code and checks that the simulation lint tables are identical.
- **Canary.** `cargo xtask canary` builds a throwaway crate inside `crates/deterministic/` with one violation per configured entry and requires every expected diagnostic. A misspelt or silently ignored entry fails here instead of letting a float through.
- The narrow float exception from PLAN.md 4.5 (a `Real` wrapper) will be allowed site by site with `#[allow]`, a spec citation and an allowlist entry when a spec requires it.

### Citations (`cite`)

In non-test code of the simulation crates:

- every numeric literal other than `0` and `1`, and
- every `const` and `static` item

must be covered by `// spec: S-xxxx` or `// measure: M-xxxx`. The comment can sit on the same line, or in the comment and attribute block directly above (or opening) an enclosing item, statement, field, variant or match arm. A blank line ends the block.

```rust
// spec: S-0042
const RELOAD_RESETS_ON_MOVE: bool = true;

fn reload_ticks(base: u32) -> u32 {
    base * 15 // measure: M-0007
}
```

- `// nocite: <reason>` in the same places marks a literal that is not behaviour, such as a buffer size of our own design. The reason is required.
- `xtask/citation-allowlist.txt` exempts whole files, again with a reason. It holds the JSONC parser, whose literals are syntax. Stale entries fail the check.
- Every `S-`, `M-` and `Q-` ID mentioned in `crates/**/*.rs` and `data/**/*.jsonc` must exist as a file in `spec/`, `measurements/` or `spec/requests/`, and a cited spec must not be retired.

`spec/` is empty at M0, so the simulation crates hold no behavioural constants yet. Anything that needs one waits for its spec or goes to `spec/requests/`.

### No stock numbers (`stock-guard`)

Stock values can't be recognised without knowing them, and this repository must never know them. So the guard enforces the structure that keeps them out. It covers every file git tracks or would add:

1. **Game-format files** (`.mix`, `.shp`, `.vxl`, `.pal`, `.csf`, `.ini`, `.map`, ... by extension) may only live in fixture directories:
   - In `tests/fixtures/synthetic/` they must match, byte for byte, what our writers generate (`cargo run -p glasnost-tools --bin glasnost-fixtures`), and `FIXTURES.manifest` must be current.
   - In any other `tests/fixtures/` directory they must be text with a `glasnost-synthetic:` line near the top.
2. **Synthetic data** (`data/synthetic/**`) starts with `SPDX-License-Identifier: CC0-1.0`, followed by a `glasnost-synthetic:` line.
3. **Measurements:** nothing under `measurements/local/` is tracked. Records with `value-visibility: local` show no numbers in the value and spread columns of their Result table.
4. **Paths:** no install paths (Steam libraries, Windows program folders, Westwood or EA folders) or home-directory paths in text files. Use `~` or a placeholder. `LOCAL.md` and `.claude/settings.local.json` stay untracked.
5. **Size:** no file over 1 MiB.

Tests that need the user's real install run in a local-only lane (opt-in, never in CI; see "Local-only lane" below); their inputs and outputs are git-ignored. A local comparison of committed synthetic data against the user's imported values needs the converter's (field, value) output. It arrives with the converter in M1 and will run only on the developer's machine.

### Synthetic ruleset

`data/synthetic/ruleset/` is a small, invented ruleset in our JSONC format (CC0). It exercises the format's shape:

- objects keyed by instance name, `inherits` lists and `^abstract` templates;
- `{"+": [...]}` set operations;
- integers in native units, and decimals as quoted strings with a unit.

`crates/deterministic/rules/tests/synthetic_ruleset.rs` checks that every file parses (so every number is an integer), carries the header and is listed in `manifest.jsonc`, and runs the layers through the resolve pipeline: inheritance, set operations, schema 1 (strict, `deny_unknown_fields`), validation, ID interning, the rules hash and `rules explain`. It also checks that `data/schema/ruleset.schema.json`, the JSON Schema generated from the schema types with schemars, is current (`GLASNOST_UPDATE_SCHEMA=1` rewrites it).

### Fixture writers

`glasnost_fmt::fixture` defines `FixtureWriter` (one synthetic file), the registry, the manifest and `check_round_trip` (encode, decode, compare, re-encode). Each format module brings its writers and registers them. `glasnost-fixtures` writes the registry's output to `tests/fixtures/synthetic/`, and the stock guard checks the committed copy byte for byte: after changing a writer, regenerate with `cargo run -p glasnost-tools --bin glasnost-fixtures` and commit the result.

Encrypted MIX fixtures use a key pair of our own (`RsaKeyPair::synthetic`), so they parse only with that key's public half, not with the Westwood key.

### Hostile input and fuzzing

Every parser in `fmt` is panic-free on hostile input: reads are bounds-checked, input-driven arithmetic is checked, allocations are bounded by the input or by `fmt::limits`, and the crate denies `unwrap`, `expect` and `panic` outside tests. `fmt::hostile::run` drives one parser and all its decoders over arbitrary bytes; `ini::hostile::run` reads a document and every stored value in every value form; `rules::hostile::run` parses JSONC, writes it back and resolves it. Two users each:

- `cargo test -p glasnost-fmt --test hostile`, `-p glasnost-ini --test hostile` and `-p glasnost-rules --test hostile` (stable, in CI): synthetic inputs, their prefixes and mutated copies.
- `fuzz/` (cargo-fuzz, nightly, outside the workspace and CI): one target per parser, plus `ini` and `jsonc`; see [fuzz/README.md](../fuzz/README.md).

### Local-only lane

`GLASNOST_GAME_DIR=<install> cargo run --release -p glasnost-tools --bin glasnost-local-lane` mounts a real install and prints counts only: MIX headers decrypted, SHP files and frames (all archives and `conqmd.mix`), VXL files and limbs under `ra2.mix`/`ra2md.mix`, IDX samples, AUD, TMP, PAL, PCX, CSF, HVA and map packs, each by error kind. `cargo test -p glasnost-tools --test local_lane` asserts 100 % on the M1 checks when the variable is set and skips otherwise; CI never sets it. The lane opens only the MIX containers at the top of the folder (`.mix`, `.mmx`, `.yro`); every other file there is counted and never read. It classifies entries with the permissive sniffer (`fmt::sniff`) and counts the strict parsers against that, so a file the sniffer calls SHP but the parser rejects shows up as a failure.

The lane also builds the game's search order (S-0005) and checks the stock outcome (the expansion archive's rules file is the one used, every required archive resolves), imports the rules and art (temperate theater), checks that the result resolves through the rules pipeline, and counts types per kind, the `sim` records of weapons, projectiles, warheads and animations, importer warnings (with the reference-field warnings by kind), art found per kind and coverage outcomes. The binary writes `coverage.csv` (key names and outcomes, no values) to `local-lane/` in the current directory, which git ignores; never commit it.

`cargo test --release -p glasnost-app snapshot -- --ignored` (with the same variable) writes viewer screenshots of a real install to the temp directory, including one of the rules view. Never commit them.

The map lane (M2): the local lane above also decodes every map it finds (`maps decoded (S-0009), no panic`, with importer warnings by kind). `GLASNOST_GAME_DIR=<install> cargo test --release -p glasnost-app --test map_lane -- --nocapture` finds every map by content, loads each with its rules (the map as the map layer), builds its scene, times the build, a CPU redraw of a 1280×720 view and 120 scrolling GPU redraws, counts provisional notes and dropped objects, and writes one screenshot per theater (plus a minimap and a close-up of the first unit) to `local-lane/`. `GLASNOST_MAP_LIMIT=n` limits the maps built, `GLASNOST_MAP_SHOTS=n` the screenshots per theater, and `WGPU_BACKEND=gl` times the GL backend.

### Provisional placeholders

Behaviour that needs a spec stays out of code; where a spec leaves a gap, the code carries an explicit placeholder tied to a spec request (see the table in "Import" below).

Q-0002 is answered by S-0005: `vfs::game` builds the game's search order by name (Table 1), honours loose files for the archives it mounts, finds members by the signed index bisection and mounts the theater and side groups per game. Loose *data* files are an opt-in mod layer (PLAN.md 4.3); with it off, a loose file that would have won is reported and never read. Archives outside the search order (for example the base game's map archives) stay browsable in the viewer but never answer a lookup.

Q-0001 and Q-0003 are answered by S-0103: `render::palette` loads palette files (×4 in 8-bit arithmetic), keeps the theater palettes in force, builds house-colour palettes from colour definitions and picks each object's palette. Shading by light (S-0104) is not applied yet; the viewer shows unshaded palettes.

## Import

The importer turns the user's install into our rules format (PLAN.md 4.3, 4.6):

1. `vfs` mounts the folder for browsing and builds the game's search order (S-0005). Loose data files are an opt-in mod layer (`GameOptions::mod_layer`, off by default, PLAN.md 4.3); with it off, a loose file that would have won is reported and never read.
2. `convert::inputs` resolves the base rules, a language rules file with a valid digest, the game-mode file the user names and the map; it reports the databases without which the original refuses to start.
3. `ini` reads each file (S-0001 to S-0003) with importer warnings.
4. `convert::layers` applies the rules layers of one game (S-0004, S-0006): registration in list order with the rank rule for references, sides, tiberiums, per-key layering with its exceptions, colour definitions (S-0103 claim 5) and the colour-adjustment table.
   Types are created by reference as S-0004 claim 13 says, from the tables in `convert::refs` (one per section kind and per game-wide section that names types). A field takes effect when its type reads its section (or its game-wide section is read); single fields are cut to their text limit (127 bytes; 63 for `HoldsWhat`, 31 for `NextParticle` and `SpawnsParticle`, 19 for `AttachedParticleSystem`, or 24 with `long_name_duplicates` off) and list fields create their items in item order; `none` and `<none>` name no type except in the four particle fields of claim 2. Find-only fields (prerequisites, country lists, `ShareSource`, the building superweapon fields, which warn for an unknown name) create nothing. The weapon fields follow claim 13's weapon-slot table, decided by `TurretCount`, `WeaponCount` and `ClearAllWeapons` as the type holds them once the section is read (`art::int_as_of`, the same reading `convert::sim` uses for the slots), in the table's index order. `ToOverlay` and the `Trailer` of aircraft and projectiles are read from an art section while the type reads its rules section (claim 14): for buildings and aircraft the one named by the image in force at that read, with the snow suffix of S-0007 claims 9 and 10 (`art::ImageWalk`, shared with the art lookup; no suffix for voxel aircraft); for projectiles only the one named by that read's non-empty rules `Image`, unsuffixed, with no fallback to the type name. Animation fields come from the animation's art section. New types fall into the rows of claim 4: `[AI]` then `[General]` before the passes (read in the layer), the passes in rank order (a new type is read in the layer if its kind's rank is at least the creating pass's), then `[CrateRules]` (wood crate, crate, water crate), `[CombatDamage]`, `[Radiation]`, `[AudioVisual]` (`Smoke` read for two fields) and `[SpecialWeapons]`, the second reading of every warhead in a layer with `[SpecialWeapons]` (row 5) and the tiberium list (row 6), none of which are read in the layer. With `unlisted_reference_unread` off, every type created by reference reads the creating layer. After the last layer, `GasCloudSys` is created if missing (claim 3); it reads no section. Within one section, keys that create types of one kind take effect in the order of the `convert::refs` tables (claim 4 leaves that order to us). A long name (claim 8) that would make a type of its own kind create copies of itself without end is stopped (claim 15, a departure, no switch): a reference requesting a kind and name, compared without regard to case, already used to create the referring type or an ancestor in this layer creates nothing, with a warning. Numbered weapon fields above 18 register weapons up to `WeaponCount` (claim 16); only the first 18 fill slots (S-0308). Two creations after the rules layers are not implemented, so `terrain_objects` and `animations` stay listed in the import record's `incomplete_registries`: the terrain objects a map's placements name and the animations the theater control file's tile animations name (S-0004 claim 3).
5. `convert::art` looks up every type's art for one theater (S-0007), with the game's per-game archives mounted.
6. `convert::emit` writes a schema-1 tree: names are byte-exact (bytes 128 to 255 map to U+F780 to U+F7FF), keys no spec maps yet stay as INI text, values the layering computes (light values in thousandths, S-0104 claim 12) replace their text (`derived`, `ini_globals_derived`), and every value carries its INI history for `rules explain`. Import errors cover the conditions under which the original would not start, and loose names that differ only in letter case (S-0005 Edge cases).
7. `convert::sim` writes the typed `sim` section (`rules::sim`): the simulation fields of the rules and art data, each written only when the layered data gives it, folded over its history (values a form cannot read and "not given" values keep the held value), with decimals as text in our grammar that reads as S-0003 reads the stored text (a test cross-checks `num::decimal` against `ini::value::decimal`). Land-type rows take only the keys of the last layer that gives the section (S-0211 claim 2), the anti-air rate follows S-0215 claim 21, locomotion classes S-0211 claim 3, the locomotor field S-0207 claim 14 (a class identifier of table T3; another form or an unknown identifier keeps the locomotor in force, with a warning), and the art fields (infantry sequences, fire frames, `Crawls`, building foundations, overlay `has_art`, an overlay's `DamageLevels` from its image section, S-0210 claim 13) are rebuilt once the art lookup has run. Animation types take the fields their creation draws read from their art sections (`RandomRate`, the bouncing flags, the chain reaction and the middle-event effects, S-0109 Import mapping). Type-name lists and references (a type's `Owner`, `[General] BaseUnit`, the gate and wall tower types of S-0112, an overlay's cell animation `CellAnim`, S-0009 claim 12, whose `none` and `<none>` clear it) are resolved to type keys by S-0003 claim 14's comparison, unknown names dropped with a warning; an overlay's `has_art` is "artwork or a cell animation" (S-0009 claim 12); the game's tech level (`[MultiplayerDialogSettings] TechLevel`), the maximum player count of the unused-house cleanup (`[Maximums] Players`, S-0009 claim 28) and the early phase's passive field (`multiplay_passive_base`, S-0009 claim 33) take the base rules' value only. A terrain type's `Strength` follows S-0102 claim 23: unset until a layer gives it, after each layer holding its section an unset strength takes `[General] TreeStrength` as it stands then (25 when absent), −1 unsets it (`quirks.tree_strength_fixed_at_first_section`); a type left unset is written without a strength, which the simulation reads as −1 (S-0009 claim 42).
   The combat fields (M4, `convert::sim::combat`, S-0301 to S-0315) follow each combat spec's Import mapping: weapons (rate of fire, burst, speed, the lepton-form ranges as decimal text, the effect and choice flags), projectiles (flags, acceleration, arm time, cluster, art `Voxel`, and `Trailer` and `SpawnDelay` from the art section of each read's non-empty rules `Image`, S-0007 claim 33; the rules keys have no effect), warheads (`Verses` as eleven exact decimal expansions of S-0003 claim 13's doubles, spread, falloff, the damage rows, debris), the shared `combat` record of infantry, vehicle, aircraft and building types (armour class by S-0305's words, ammunition and reload, immunities, debris and death fields, targeting flags, the five threat coefficients, art muzzle positions and turret offset), the weapon slots of S-0308 claim 1 (both forms, with the clear-weapons flag applied at each reading of the section), the vehicle burst delays and firing frames, the building art fields (aim shift, height, voxel turret, pixel offsets, delayed fire), country factors and veteran lists, the building `Cost` (S-0311 F1, S-0314 claim 5), the three difficulty rows (`sim.difficulty`) and the game-wide combat values. Weapon `Speed`, the ranges, `AirRangeBonus`, `BallisticScatter` and `FireSupress` given as −1 count as not given. Type names in the new fields resolve to type keys where a type of that name exists and keep the name as written otherwise (a field S-0004 claim 13 does not list as creating, or a name that claim 8 duplicates); every registered weapon, projectile, warhead and animation gets a `sim` record, empty for one that read no section (it keeps the engine defaults of its kind); fields the schema documents as type keys (veteran lists, `HarvesterUnit`, the crew types) drop unknown names with a warning. The importer warns for the bad-data cases of the combat specs' Edge cases. `Decimal::value` reads text at 24 bits (S-0003 claim 6), so a versus value that is not exactly a single needs a 53-bit reading of its text (`num::decimal::nearest_double`) to recover the double.
8. `rules::resolve_ruleset` applies mod patch layers, inheritance and set operations (only in our own collections, never inside imported INI data), types, validates, interns IDs and hashes.

Every quirk switch of the implemented specs has a field in `ini::Quirks` (including S-0003's `percent_list_integer_prefix` and `list_items_untrimmed`, the latter shared by S-0303, S-0311 and S-0312 list items), `vfs::GameQuirks`, `convert::layers::LayerQuirks`, `convert::art::ArtQuirks`, `convert::sim::SimQuirks` (S-0308's `clear_weapons_any_turret_count`, S-0309's `coefficient_zero_replaced`, S-0102's `tree_strength_fixed_at_first_section`), `convert::theater::TheaterQuirks`, `convert::map::MapQuirks` or `render::palette::PaletteQuirks`, defaulting to the original's behaviour; the import records them under `import.quirks`. The renderer's and the map viewer's switches are fields of `render::projection::ProjectionQuirks` (S-0101), `render::compose::ComposeQuirks` (S-0102 compositing), `render::light::LightQuirks` (S-0104), `render::voxel::VoxelQuirks` and `render::voxel::RecoilQuirks` (S-0105), `render::overlay::OverlayQuirks` (S-0112), `render::palette::PaletteQuirks` (S-0103) and `app::mapview::quirks::ViewQuirks` (S-0102 draw order and placement, S-0108 building frames), each with `named()`. `rules::quirks::tests::every_spec_quirk_has_a_switch` checks that every switch the simulation specs, S-0006, S-0009, S-0010 and S-0107 name is a field of `rules::Quirks` or listed with its owner in `EXTERNAL_QUIRKS`; `app::mapview::quirks::tests::every_rendering_spec_quirk_has_a_switch` checks that every switch `spec/rendering/S-01*.md` names is a field of one of the structs above (or of `rules::Quirks`, `LayerQuirks`, `ArtQuirks` or `SimQuirks`) or is listed in `app::mapview::quirks::NOT_IMPLEMENTED` with its reason (the table below). Two S-0009 switches of `MapQuirks` are not consulted yet, because our engine has no lobby and draws no preview markers: `lobby_counts_zero_waypoint` and `preview_markers_from_header`. Four S-0006 switches of `LayerQuirks` are not consulted either, because the importer imports one game, the first of its session, without campaigns or the mode list (Q-0006): `persist_global_overrides`, `persist_tiberium_overrides`, `mission_rules_before_reset` and `mode_number_first_wins`. ## Simulation (M3)

`glasnost-sim` runs the game rules on the typed ruleset and map. Everything in it is integers and the soft-float types of `glasnost-num` (S-0205: IEEE binary32/64 in integers, round toward zero under `quirks.chop_rounding`), with ordered containers only.

- **Rules and data.** `rules::SimRules` is built from a resolved ruleset (`SimRules::new(&resolved.ruleset, &resolved.sim_rules_hash)`): typed per-kind tables, the 105 quirk switches of `rules::Quirks` (every one defaulting to the original; `refused_death_keeps_unit` of S-0107 claim 17 is not consulted, since M3 has no death handling), and engine defaults cited to their specs. A type without a locomotor field has the teleporting locomotor (S-0207 claim 14); vehicles with the driving locomotor drive and infantry with the walking one walk, and every other locomotor is not moved in M3. `consts` holds the spec constants given as decimals, as checked bit patterns.
- **A game.** `load::new_game(rules, map, catalogue, setup)` follows S-0009 and S-0202's table *Draws during map loading*: the early phase of start positions on blank cells (lists 1 and 2, the assignment against list 2, with the base rules' passive fields, claims 17 to 20 and 33; `starts`, with the start-cell variant of the nearby-cell search, `path::start_cell`), the initial fill, the overlay type stream placed overlay by overlay (`overlays`: the slope condition of claim 12, high-bridge cells as each overlay is placed, wall connection bits, low-bridge end markers with their pieces' draws), the overlay data stream, the first recalculation pass, the vein rebuild with its draws (claim 14), the tile animations each recalculation starts with their creation draws (S-0010 claim 19, S-0202 claim 10: the first recalculation of a cell before the second pass, then at most one per cell from the second pass on, in play too; `load::recalc_cells`), the pre-placed objects (with the visceroid draw of a vehicle's placement and its follower-car link, claim 41), the second pass, the late phase (list 3), the unused-house cleanup (claim 28: only in a game with no AI house, S-0412 claim 12, and fewer human slots than the base rules' maximum player count; a removed house loses its pre-placed objects, takes no position and gets no starting units; `House::removed`), the owners of the map's walls (S-0210 claim 14), the starting units (`starting`, claims 45 and 46: the placement search's acceptance test reads the ground occupants of the ground layer only and takes as the nearest the one whose reference point lies nearest the cell corner by the table root, ties by the ground list's order), the game-start pass of S-0010 claim 12 (a third recalculation of every legal cell, with its tile animations) and the bridge spans of S-0010 claim 25, whose low spans give their bands the bridge-body mark (`Cells::bridge_body`, `glasnost_map::bridges`; the burrowing test of S-0010 claim 17 is to read it). Terrain recalculation itself is `glasnost-map`'s (S-0010, S-0211). `GameSetup` gives each house a role (player, neutral, special), whether it is an AI house (`HouseSetup::ai`), the unit-count setting and the bases setting. `load::sandbox_setup` is our viewer's setup: one house per object owner of the map, no start positions and no starting units.
- **Wall connection bits.** `walls` keeps a wall's overlay data value as 16 × damage stage + connection bits (S-0112 claim 7), recomputed when a wall is placed from the map's overlay list, when crushing removes one, and when a gate or wall tower is placed or destroyed (`quirks.gate_tower_fixed_cells`). - **A tick.** `tick::step` runs S-0203's parts in their places: the turn pass over the update order (with S-0203's removal skips and second turns), each object's behaviour part (`process`, S-0215), its locomotor (`drive` with `tracks`, S-0207 and S-0206 claim 12; `walk`, S-0208), its infantry sequence (`infantry`, S-0107), then the orders (`orders`, S-0213), then the tick number. Occupancy is `cells`/`occupancy` (S-0209), crushing `crush` (S-0210), passability and regions `passability`/`regions` (S-0211, S-0212), pathfinding `path` (S-0212) behind the `Pathfinder` trait, over (cell, search layer) pairs, with the corridor of claims 13 to 14 in `corridor` (sectors and connections are derived data, rebuilt with the regions). ## Simulation (M4: combat)

Combat lives in `glasnost_sim::combat`, driven from the tick pipeline and the behaviours of M3; every phase runs in S-0203's places (no component picks its own order). Its rules are typed in `combat::data` (`CombatRules`, built inside `SimRules` from the schema's combat fields: weapons, projectiles, warheads with their versus values read at double precision, per-type `TypeCombat`, countries' multipliers, the general values and the difficulty rows). The quirk switches the combat specs name are in `rules::Quirks` (236 switches now, each defaulting to the original), plus `clear_weapons_any_turret_count` and `coefficient_zero_replaced` (importer, `convert::sim::SimQuirks`) and `percent_list_integer_prefix` (`ini::Quirks`); the quirk inventory test checks every switch the simulation, movement, infantry, rendering and combat specs propose.

- **Firing (S-0301, S-0310, S-0313).** `check` is the firing check in S-0301 claim 9's rank order, with S-0310's aiming answers (turret and body facing, the building aim point); `fire` makes a shot (burst counter, the delay kinds and their draws, ammunition and reloading, firing-frame sync, the full delay F1 and the reload F3), `position` the fire point (the 3 × 4 single-precision matrices of S-0313 F1, burst alternation, building pixel shifts F3), `behave` the firing parts of the behaviours (vehicles S-0310 claim 9, infantry S-0107 claim 11, buildings S-0215 claim 32 with the turret snap), and `ballistics` the arc speed and reachability.
- **Weapons and acquisition (S-0308, S-0309).** `weapon` chooses the slot by table P (with table N, gattling and switching types, elite slots), the mean damage of a healer for acquisition and the versus lookup (S-0304, S-0305); `acquire` holds the searches (ring order F2, candidates by table C, threat F4 to F9, early stops, the timer draw first), retaliation, anger, expected remaining health and the per-tick search after an actor's processing, area guard and hunt.
- **Projectiles (S-0306, S-0307).** `projectile` launches (straight and arcing pitch, scatter F5), flies (turning F7, steering F10 to F12, the rows of tables T1 and T2), detonates (detonation point, cluster draws, airburst children) and removes shots; projectiles are kept in `World::projectiles` in update order, with IDs from the object counter. `range` is the range test (elevation bonus F2, measured and source points, the high-bridge refusals) and `lof` the line-of-fire walk.

- **Death, veterancy, healing, suppression (S-0311, S-0312, S-0314, S-0315).** `death` removes killed objects (nearby point F2, debris, death weapons, infantry death sequences, crew and survivors, building destruction, terrain objects), `veterancy` ranks and abilities (and the experience a pre-placed object starts with), `heal` self-healing, `fear` suppression and panic.
- **Effects.** `combat::effects` lists the cosmetic events of a tick (animations, detonations, shots, deaths) in `World::effects`, which is not state (it is skipped by saves and hashes); the viewer draws them.
- **Repair steps (S-0314).** `heal::repair_step`, `step_size`, `step_cost` (F2 with our engine's departure) and `building_repair_step` are the step rules; nothing asks for a step yet (depots, hospitals and the repair order wait for the structures and economy topics), and a building's step cost is F2 on S-0408's adjusted cost (`seams::building_adjusted_cost`, which calls `econ::sell::adjusted_cost`).
- **Input rules.** S-0214's armed, healing actor, claim 6 (d) and (e), rows I16, I21, GC4, AC8, ACC, BC3, BC4, k1, table R and the idle order read the weapon choice, the range test, the firing check's legality answer and veterancy abilities.
- **Seams.** Not modelled yet, each left where its topic plugs in: garrisons and bunkers, transports and open-topped passengers, cloaking and disguise, berserk, mind control, spawned aircraft and flight (`weapon::in_air` is false), parasites, crates, bridges (deck damage), smudges, particles, animation playback (a weapon that waits for an animation detonates at once), sides (no survivors are created; the crew type is the technician), the production cost factors (1.0), the map's inert and harvester-immune flags, turret-locked weapons (not imported), the weapon cursor flags of S-0214 rows I17 and I18, and economy, production, power and shroud (S-04xx, M5). Where a behaviour or combat rule asks an M5a topic (slave miners and the harvesters' guard rules of S-0402, available credits and payment of S-0404, short of power of S-0405, adjusted cost and refund of S-0408, the defeated state of S-0414), it calls `glasnost_sim::seams`. The harvesters' guard rule, short of power, available credits, payment, the adjusted cost, the refund and the defeated state are connected to their M5a topics; the slave group's parts answer "the other topic's condition does not hold" until their topics fill them in.
- **Claim ledgers.** `docs/m4-claims/S-03xx.md` lists every claim of each combat spec as tested, seam, partly or not implemented, with the tests that check it (`crates/deterministic/sim/tests/claims_s03*.rs`, each citing `// spec: S-xxxx claim N`). `testkit::combat_ruleset` and `testkit::game_with` give the invented combat ruleset and an empty-map game for such tests.

## Simulation (M5a: economy and base building)

- **Power, shroud and radar (S-0405, S-0409, S-0410).** `econ::power` keeps each house's totals and blackout (`HousePower`), works them out in the house update when an event has made the house due (placement, removal, owner change, switch, health noticed in the building's own turn, blackout start and end), and answers `low_power` and `fraction` (the double that S-0403 claim 5 reads). `in_operation` is the live test of claim 8 and `firing_answer` is table T1 at S-0301 rank 4 (`combat::check`); the one-off effects (control-centre count, gap field, super-gap end) run in the building's own turn through `econ::events::turn`. `power::switch` applies the power orders. `econ::shroud` keeps per player house the cover count, hostile gap count and marks of table S1 (plus one shared off-map state), applies sights in the objects' turns and at building placement, runs the re-cover sweep before the turn pass and the optional regrowth, gap fields, the spy satellite's reveal and the whole-map re-cover (taken back and re-applied in object order), the reveal on fire (`combat::fire::shot`), area reveals for other specs, `defeat_reveal`, discovery, the point test of S-0110 claim 8 and the query `explored`. `econ::radar` rechecks claim 1 in the house update after an event (power first, then radar and the spy satellite); `on_defeat` turns radar on for good and reveals the map. `econ::minimap` holds the radar map's pure functions (point grid F1, scale F2, cell at a pixel F3, object pixel F4, flash F5, terrain mean F6, tile colour F7, overlay table T1, listing, arrivals and `compose`) for the viewer; nothing there is game state. Seams, each a small function in `econ::power` that answers "no" or 0: pulses and locks, being erased or drained, chargers, absorbed passengers, engineers, occupants; the superweapon charge hold (claim 15) and the super-gap's deploy behaviour (claim 16); what a disabled vehicle cannot do. `production::power_changed` (S-0405 claim 11) works out every line's step period again; S-0409 claim 11 reads `victory::defeated`. Ledgers: `docs/m5-claims/S-0405.md`, `S-0409.md`, `S-0410.md`.
- **Production, tech tree and the sidebar's rules (S-0403, S-0404, S-0407, S-0411).** `econ::production` holds every house's lines in creation order (`World::econ.lines`), the build time F1 to F7 (`build_time_of`, `period_of`, on the power fraction `power::fraction`, refreshed by `power_changed`, which S-0405's house update calls), the price with cost bonuses, pad term and free unit (the adjusted cost is `econ::sell::adjusted_cost`, S-0408's), available credits and payment (`available_credits`, `pay`, behind `seams::available_credits` and `seams::pay`), pay-as-you-go steps in tick row 6, holds, cancels and refunds, the queue, the release of done units (primary, else last acquired) and the factory checks of S-0404 claim 8 (called from `econ::events`). An item's object is created at the start (the creation draw of S-0404 claim 11) and stays off the map until it is released or placed. `econ::tech` gives the tech-tree answer (override, secret type, tech level, country lists with the index wrap, stolen tech, superweapon setting, prerequisites with groups and upgrades, build limits), the present, owned and ever-built counts, the taken-up set (which is also the icon set) and its rechecks at the house update (`tech::house_update`; a recheck returns the types it removed), the queue-time limit and `assign_secret_labs` for S-0412's game start. `econ::sidebar` has the click tables of S-0411 claims 4 and 5 as pure functions (`click`), the icon states, the legality of production orders (`legal`, which `orders::issue` applies to every house), and, at every player house's update, the cancel and cancel-all orders of S-0411 claim 2 and S-0404 claim 9 for the types a recheck removed (`removal_orders`; the start of a sale removes nothing) and the automatic release order of claim 9. Darkening (claim 3) and the at-limit tests use the build-limit answer with the production allowance (`tech::at_limit`). A build order is applied when `tech::could_make_limit_only` holds (S-0407 claim 13; Q-0122). The superweapon setting (`setup::superweapons_allowed`) and don't-score vehicle entries (`victory::unscored_vehicle_entries`) come from S-0412 and S-0414. Seams: free docks (every aircraft factory has one until M6), vehicle-thief take-overs and infiltration (`tech::infiltrated`, for the special-abilities specs). Ledgers: `docs/m5-claims/S-0403.md`, `S-0404.md`, `S-0407.md`, `S-0411.md`.
- **Placement, selling, repair, deploy and pack-up (S-0406, S-0408, S-0415).** `econ::placement` has the cell test (`cell_test` with a `Test`: the placing house, whose walls the exceptions of claim 8 accept, whether place-anywhere counts, and an object to ignore), the foundation cells (the 8-cell 3 × 3 word), adjacency (F1), explored ground, `place_legal` (what `orders::issue` asks of a place order with a cell), the input helpers `click_cell` and `cursor_shroud_result`, and `place_building`, which `production::place` calls: the factory condition of claim 1, then either an upgrade (`upgrade_target`, `add_upgrade`, F5) or the cell test and `put_on_map`. `put_on_map_facing` is the one core for a place order, a deploy and a filling wall: walls underneath removed by the silent wall sale (claim 9), a wall type turned into its overlay (claim 10), otherwise the building put at the cell centre at the surface height in its construction state (`begin_construction`; `objects::place_with` passes `by_order` to the events), then the wall fill for a place order (claim 11). The construction behaviour (`deploy::process_construction`) and the selling behaviour (`sell::process_selling`) are dispatched from `process.rs`; both run every tick and end when (*n* − 1) × *d_b* ticks have passed (`sell::buildup_ticks`, S-0108 claim 5). `econ::sell` has the refund (F1, on `production::cost_factors`) and main's adjusted cost (F2), sellable and repairable, the sell order (building, upgrade, vehicle on a building cell), the wall sale (`wall_sale`, silent or not), the repair switch and the building's repair step in its own turn (`sell::building_turn`, via `econ::events::turn`, on S-0314's `building_repair_step`). `seams::building_adjusted_cost` and `seams::building_refund` now answer. `econ::deploy` has the vehicle's *unload* by the ranks of S-0415 claim 1 (`process_unload`, ranks 1 to 3 handed back), the attempt, refusal, turn and completion (claims 2 to 6, state in `DeployState`, reset by every deploy order), `packs_up` (S-0213 claim 12) and the pack-up's end (`pack_up`, claims 10 and 11). Sounds are `Effect::Sound` events (deploy, pack-up, sell, cannot-deploy, unit sold) for the viewer. Seams: the to-tile tileset test (no morphable flag in the catalogue), docked units, absorbed passengers, garrisons and sale survivors (no sides), mind control, deploy-readiness states other than health, map-placed upgrades (still separate objects). Ledgers: `docs/m5-claims/S-0406.md`, `S-0408.md`, `S-0415.md`.
- **Skirmish setup, country bonuses, victory and defeat (S-0412, S-0413, S-0414).** A skirmish is started in three steps: `econ::setup::skirmish(rules, players, settings, unit_count, seed)` builds the `GameSetup` (the players in house order, each a `Player` with name, country, start, AI flag and lobby `HouseValues` (team, handicap, colour, observer), then the neutral and special houses; `Settings` holds credits, short game, superweapons, crates, build off ally, redeploy and the all-base-units mode, each `None` for the rules' default); `setup::resolve_lobby` (optional) settles random countries and colours on its own lobby stream, so the game's stream is untouched; then `load::new_game` (or `Replay::new`) refuses a setup S-0412 forbids (`LoadError::Setup`), creates the houses with their credits, difficulty index and row (`house_values`) and, for every non-sandbox game, runs `setup::start_game` after the starting units: crate count, extra credits, start alliances, wall-owner rewrite, colour fields and secret labs. The accessors `credits_setting`, `short_game`, `superweapons_allowed`, `build_off_ally`, `redeploy`, `observer`, `person_played`, `wall_owner` and `colour_field` answer other topics. The outcome is `victory::outcome(&World) -> Option<Outcome>` (`Some` once the game is over, with each player house's `Verdict`); `victory::verdict`, `victory::defeated` and `victory::ended` answer per house and game. Seams: crate placement, superweapon granting, the all-base-units mode (refused), observer positions, aircraft flight, mind control, erasure, passengers and the nominal-survivor condition. Ledgers: `docs/m5-claims/S-0412.md`, `S-0413.md`, `S-0414.md`.
- **Viewer live sandbox (M5a).** The *game on load* option starts either the sandbox game (every owner's objects, as in M3) or a skirmish (`live::skirmish_setup`: one human house and one computer house of the rules' first open countries, no starting units beyond the base units, the fixed sandbox seed), in which `glasnost_ai`'s script plays the computer house through orders every `THINK_PERIOD` ticks. ## Tests

```sh
cargo test --workspace          # unit tests, render tests, dependency rule
cargo xtask check               # the checks above
```

`crates/render/tests/offscreen_quad.rs` renders the palette quad on a real or software GPU and compares every pixel with the CPU palette lookup. Without an adapter it skips, unless `GLASNOST_REQUIRE_GPU=1` is set (CI sets it and installs lavapipe). `WGPU_BACKEND=gl` runs it on the native GL backend. `crates/render/tests/webgl2_shaders.rs` translates every shader to GLSL ES 3.00, so constructs WebGL2 can't express fail without a browser.

The browser lane is described in [web.md](web.md).

## CI

`.github/workflows/ci.yml` runs these jobs:

- rustfmt;
- clippy, native and wasm32;
- tests, with lavapipe and `GLASNOST_REQUIRE_GPU=1`;
- `cargo xtask check`;
- cargo-deny licence check against `deny.toml` (GPL-3.0-or-later compatible licences only);
- the determinism gate (`cargo xtask gate`: native release and wasm32 under node);
- the release web build;
- the browser lanes:
  - WebGL2 on Chromium, Firefox and WebKit (WebKit non-blocking until it has run green);
  - optional WebGPU on Chromium.

CI uses synthetic data only.
